# Format de description d'un connecteur

- **Statut** : validé par le mainteneur le 29/09/2026
- **Dernière révision** : 2026-10-26

## Résumé

Un connecteur partagé se décrit dans un fichier YAML, `connectors/<nom>/connector.yaml`, validé par `connectors/connector.schema.json` (JSON Schema 2020-12). L'unité du format est la fonction servie avec son appel : ce que l'agent voit (nom, description en anglais, schéma d'entrée strict, classe, exemples, refus nommés) et la requête derrière (méthode, chemin, répartition des arguments, pagination, sortie). Ce qui ne se décrit pas reste du code écrit à la main, référencé depuis le fichier. Le bloc `connector` dit aussi ce qu'est un compte : les champs de son credential, ses réglages non secrets (région, adresse), son authentification, consentement OAuth d'une personne compris, et, pour un compte rattaché chez un tiers qui héberge les comptes de ses utilisateurs, l'identité de ce compte et les champs que fournit l'hôte. La [fabrique](fabrique.md) en tire Python et TypeScript ; cinquante et un connecteurs ont leur description, et tout client ajouté à la lib entre au format.

## Contexte

- La lib porte une centaine de clients Python écrits à la main. Au relevé du 29/09, le schéma d'un outil y vient de la signature et sa description de la docstring ; aucune classe n'est déclarée, aucun refus n'est nommé, la confirmation se fait au cas par cas.
- Le paquet d'oto 2 sert des fonctions qui déclarent classe, exemples, refus et résumé de confirmation. Elles ne sont pas des outils MCP : elles se trouvent, se lisent et s'appellent par les six outils figés du paquet (oto-pkg : docs/conception/connecteurs-et-comptes.md).
- Un connecteur partagé sert deux langages : Python pour la lib, TypeScript pour le paquet. Écrit deux fois à la main, il divergerait ; d'où une description unique.
- Relevé du 29/09 sur 114 connecteurs de la lib, par lecture du code et à seuil arbitraire : 54 enveloppes d'API REST, 44 REST avec logique, 16 hors format (3 navigateur, 7 données ouvertes ou base embarquée, 3 SDK, 2 traitement local, 1 asynchrone).
- Se décrit : authentification (clé, basique, client credentials, consentement d'une personne), réglages d'un compte, URL de base, verbe et chemin, répartition des arguments, corps formé d'un argument objet entier, arguments placés sous des clés emboîtées du corps à côté de constantes du même parent, constantes et en-têtes constants, encodage JSON d'un argument, schéma, table des erreurs et leur caractère rejouable, signal de refus du service (clé refusée, crédits épuisés, y compris sous un 200 ou un 400), délai d'un appel, par connecteur ou par fonction, corps multipart qui envoie un fichier en transit de l'appelant, contrôles simples avant l'appel et sur la réponse, projection de sortie, coût d'un appel (pire cas avant, quantité relue après), travail asynchrone et sa relève, pagination, rythme maximal du tiers, sonde et solde d'un compte payant. Reste à la main : fusion de plusieurs appels, refus locaux que les contrôles déclarés ne disent pas, construction d'un mail, identité opérée.

## Objectifs et non-objectifs

- Une seule source par connecteur partagé, d'où sortent les deux langages.
- Le contrat vu de l'agent s'écrit une fois : classe, exemples validés, refus nommés, en anglais.
- Un fichier invalide est refusé avant toute génération.
- Ce qui ne se décrit pas reste possible, par une entrée `handwritten` dont le schéma, la classe et les refus restent déclaratifs.
- Hors objectif : convertir les connecteurs existants. Ils restent en Python tels quels ; seuls les nouveaux connecteurs partagés et ceux qu'oto 2 demande entrent au format, et un existant réclamé entre comme un nouveau.
- Hors objectif : décrire un connecteur propre à un hôte, écrit dans l'hôte au contrat du paquet (oto-pkg : docs/conception/connecteurs-et-comptes.md).
- Hors objectif : porter un secret, un compte ou une activation. Le fichier nomme les champs du credential et les réglages, et décrit le consentement ; garder, chiffrer, rafraîchir et résoudre relèvent de l'hôte.

## Conception

### Le fichier

- Un dossier par connecteur sous `connectors/` : son `connector.yaml` et, si besoin, son code écrit à la main dans les deux langages. `connector.name` est le nom du dossier.
- YAML, déclaré en version 1.2, validé par un schéma JSON 2020-12 que les deux langages savent lire. Le fichier porte en tête `# yaml-language-server: $schema=../connector.schema.json`.
- Trois blocs : `connector` (un par fichier), `functions` (au moins une), `exposure` (facultatif). Toute clé inconnue fait refuser le fichier.

### Le bloc `connector`

| Champ | Obligatoire | Sens |
|---|---|---|
| `name` | oui | Identifiant stable (`^[a-z][a-z0-9_]*$`), premier segment des outils. |
| `label` | oui | Nom affiché. |
| `namespace` | oui | Préfixe des outils exposés, souvent égal à `name`. |
| `version` | oui | Version du connecteur, semver : elle monte avec tout commit qui change sa description ou son client (« Contrôles »). |
| `api_version` | oui | Version de l'API tierce, telle que l'éditeur la nomme. |
| `base_url` | sauf `base_urls` ou tout `handwritten` | Racine `https://` des chemins d'appel, sans `/` final ; gabarit possible sur les réglages. |
| `base_urls` | non, exclusif de `base_url` | Une racine par valeur d'un réglage `choice` : `{ setting: region, values: { us: …, eu: … } }`. |
| `auth` | oui | Mode d'authentification, voir « Le compte ». |
| `credential` | sauf `none` et `oauth2_user` | Champs fournis par le consommateur : `name`, `label`, `secret` (booléen), `holder` (`account` par défaut, ou `host`), voir « Le compte ». |
| `account_identity` | non | Identité d'un compte rattaché chez un tiers : `name`, `label`, `pattern` (expression ancrée), citée par `base_url` seulement, voir « Le compte ». |
| `settings` | non | Réglages non secrets d'un compte, voir « Le compte ». |
| `modes` | oui | Qui peut porter un compte : `platform`, `byo_user`, `byo_org`. |
| `timeout_s` | non (30) | Délai d'un appel, en secondes, de 1 à 300 (le plafond qu'exécute le paquet d'oto 2) ; une fonction peut déclarer le sien. |
| `quota` | non | Quota par défaut sur une clé de la plateforme ; n'existe que si `modes` contient `platform`. |
| `query_arrays` | non | Encodage des listes en query : `repeat`, `brackets`, `comma`. |
| `headers` | non | En-têtes constants de toute requête : `{ Notion-Version: "2025-09-03" }`. Jamais un secret ni l'en-tête d'authentification. |
| `rate_limit` | non | Rythme maximal du tiers, par credential : `{ requests: 4, seconds: 1 }`. |
| `probe` | non | Sonde de la connexion : `{ function: get_company, non_empty: [scopes] }`, une lecture sans argument requis, jamais décomptée d'un quota ; chaque chemin de `non_empty` doit être non vide dans sa réponse ; `balance`, le solde d'un compte payant (voir « Sonde à solde »). |
| `errors` | oui | Table commune à toutes les fonctions : `status` (un ou plusieurs codes HTTP), `code` (refus nommé), `message` (anglais), `retryable`, et facultatifs `body` (condition sur le corps) et `marks_account` (voir « Signal de refus du service ») ; la première entrée qui s'applique l'emporte. |

### Le compte

Un compte garde tous les champs que déclare `credential` (les secrets chiffrés par l'hôte) et ses réglages, `settings` : `name`, `label`, `type`, et selon le type, `choice` (`choices`, liste fermée, `default` facultatif : `{ name: region, label: Data region, type: choice, choices: [us, eu], default: us }`), `text` (`pattern`, expression ancrée : `{ name: domain, label: Domain, type: text, pattern: "^[a-z0-9-]+$" }`) ou `url` (adresse `https://` libre, saisie par un admin : serveur d'un standard, site).

Un réglage n'est cité que par une adresse. `base_url`, `token_url` et `authorize_url` sont des gabarits : `https://{domain}.example.net` (domaine d'un tenant), `{server}/xapi/v1`. Un réglage `url` (ou une valeur de `from_token`) ne se cite qu'en tête, à la place du schéma et de l'hôte ; un autre réglage, qu'après `https://`. `base_urls` et `token_urls` donnent une adresse à chaque valeur d'un `choice`, quand les hôtes ne se déduisent pas l'un de l'autre. L'exécution garde ces adresses : `https` seul, jamais un hôte qui résout vers une adresse interne, aucune redirection suivie ; une valeur `text` ou `choice` ne porte que lettres, chiffres, `-` et `_`.

`auth.kind`, chaque secret nommant un champ de `credential`, jamais une valeur :
- `api_key` : `in` (`header` ou `query`), `name` (de l'en-tête ou du paramètre), `key`, `prefix` en en-tête seulement : `{ kind: api_key, in: header, name: X-Claap-Key, key: api_key }` ;
- `bearer` (`token`) ; `basic` (`password`, et `username` facultatif : `Authorization: Basic base64(username + ":" + password)`, le texte encodé en UTF-8 ; sans `username`, l'identifiant est vide, `Basic base64(":" + password)`, pour un service qui prend sa clé seule en mot de passe : `{ kind: basic, password: api_key }`, décidé le 2026-10-21) ;
- `oauth2_client_credentials` : `token_url` ou `token_urls`, `token_request` (`json`, `form`), `client_auth` (`body` ou `basic` : où vont l'identifiant et le secret du client), `client_id`, `client_secret`, `scope` et `expires_in_default` facultatifs ;
- `oauth2_user`, le consentement d'une personne (code d'autorisation) : `authorize_url`, `token_url` ou `token_urls` (corps en formulaire), `client_auth`, `scopes`, `authorize_params` (constantes, jamais un paramètre que pose l'hôte : `client_id`, `redirect_uri`, `state`…), `pkce: S256`, `refresh` (`refresh_token` avec `rotates` booléen, `exchange` avec `exchange: { grant_type, token_param }`, ou `none`), `expires_in_default`, `identity: { function: get_me, path: userPrincipalName }` (qui a consenti, pour nommer le compte : une lecture sans argument requis), ou, quand l'API n'a pas de telle lecture, `identity: { url, path, scopes }` : une adresse complète en `https`, fixe (ni gabarit, ni query), hors de `base_url` (le service d'identité commun du fournisseur), lue en `GET` avec le jeton et sans argument, et les droits qu'elle exige, que le consentement demande à chaque niveau, `from_token: [instance_url]` (champs de la réponse de jeton gardés avec le compte, citables par `base_url`) ; à la place de `scopes`, `access_levels` et `scope_implies`, les niveaux d'accès ([niveaux d'accès](niveaux-d-acces.md)) ;
- `none`.

En `oauth2_user`, `credential` est interdit : les jetons du consentement ne sont pas des champs, et `client_id`/`client_secret` appartiennent à l'application OAuth (celle de l'hôte par défaut, celle de l'organisation si elle en pose une), pas au compte ni au fichier.

**Compte de l'hôte et compte rattaché.** Un champ de `credential` porte `holder` : `account` (par défaut : saisi avec le compte) ou `host` (fourni par l'application hôte, une fois pour toutes ses organisations ; jamais stocké avec le compte, montré ni saisissable). Un compte rattaché chez un tiers qui héberge les comptes de ses utilisateurs (une messagerie hébergée : LinkedIn, WhatsApp…) déclare `account_identity` : `{ name: account_id, label: LinkedIn account, pattern: "^[A-Za-z0-9_-]{1,64}$" }`, l'identifiant du compte chez le tiers, une valeur par compte. Il ne se cite que dans `base_url` (`https://api.unipile.com/v2/{account_id}`), ou dans chaque adresse de `base_urls`, après l'hôte (jamais à la place du schéma ou de l'hôte), et dans aucune autre adresse ; aucun argument, paramètre de chemin, de requête, de corps ou d'en-tête, ni aucune constante ne porte son nom, ni aucun champ de `credential`, réglage ou valeur de `from_token`, et la fabrique le refuse : l'agent ne le fournit jamais, il vient du compte que la règle de partage de l'hôte a désigné. Un connecteur dont tous les champs sont `holder: host` est valide : le compte n'a alors que son identité. L'hôte assemble à l'appel son secret, les champs du compte et l'identité ; il écrit l'identité par un seul service qui la vérifie auprès du tiers, jamais par une saisie (la clé de l'hôte atteint tous les comptes de son abonnement).

```yaml
connector:
  name: linkedin_unipile
  base_url: https://api.unipile.com/v2/{account_id}
  auth: { kind: api_key, in: header, name: X-API-KEY, key: api_key }
  credential:
    - { name: api_key, label: Unipile API key, secret: true, holder: host }
  account_identity: { name: account_id, label: LinkedIn account, pattern: "^[A-Za-z0-9_-]{1,64}$" }
```

### Le bloc `functions`

| Champ | Obligatoire | Sens |
|---|---|---|
| `name` | oui | Un verbe et son objet : `list_estimates`. |
| `class` | oui | `read`, `write` ou `sensitive`. |
| `act` | non (déduit de la classe) | La fonction engage ou détruit (envoi, corbeille, archive, déplacement) : booléen, `false` par défaut pour `read`, `true` pour `write` et `sensitive`. Une simple préparation, comme un brouillon, déclare `act: false`. Jamais `false` sur `sensitive`, jamais `true` sur `read` (la fabrique refuse). |
| `scopes` | si le connecteur a des niveaux d'accès, interdit sinon | Les droits OAuth que la fonction exige, tous ([niveaux d'accès](niveaux-d-acces.md)). |
| `description` | oui | En anglais, 1000 caractères au plus (borne du paquet d'oto 2) : ce que l'agent lit. |
| `input` | oui | JSON Schema 2020-12 d'un objet strict (`type: object`, `additionalProperties: false`, `properties`), servi et validé tel quel. Une propriété peut porter `personal: true` (« Donnée personnelle », ci-dessous). |
| `examples` | oui, au moins un | `title` et `input`, chaque `input` validé contre `input`. |
| `refusals` | non | `code`, `when` (statut HTTP ou condition), `message` : surcharge ou complète la table commune ; sous un statut seulement, `body` et `marks_account` comme dans la table. |
| `checks` | non | Contrôles de l'entrée avant l'appel, chacun nomme un refus : `{ kind: equal_sums, refusal: entry_unbalanced, items: ledger_entry_lines, fields: [debit, credit] }` (sommes égales, chaînes décimales sommées exactement). |
| `expect` | non | Contrôles de la réponse, chacun nomme un refus : `{ kind: non_empty, refusal: pdf_missing, path: public_file_url }`. |
| `call` | sauf `handwritten` | `method`, `path` relatif avec `{param}`, puis `query`, `body` (envoyé quelle que soit la méthode, `DELETE` compris), `headers` qui associent un nom côté API à un argument ; dans `body`, la valeur d'une clé peut aussi être une table de même forme, emboîtée (« Le corps emboîté ») ; `body` peut aussi nommer un seul argument, un objet strict, qui forme le corps entier (« Le corps entier ») ; `constants` (`query`, `body`, `headers`) : des valeurs envoyées à chaque appel, hors du schéma, comme `{ body: { draft: true } }` ; `encode` : `{ filter: json }` sérialise un argument structuré en une chaîne ; `files` : les parties fichier d'un corps multipart (« Fichiers »). Chaque argument va à un seul endroit, chaque nom côté API reçoit une seule valeur. |
| `handwritten` | exclusif de `call` | `python` (`module`, `function`) et `typescript` (`file`, `export`). |
| `pagination` | non | `kind` (`cursor` ou `page`), `request_param` (l'argument qui porte le curseur, placé en query ou au corps, emboîté ou non), `next`, `more` facultatif (booléen de la réponse, `false` à la dernière page : `has_more`), `total` facultatif, `max_pages`. Présente, elle ajoute `all_pages` et `max_pages` au schéma servi. |
| `output` | non | `items` (chemin de la liste), `strip` (clés retirées, chacune par son chemin : « Retirer de la sortie »), `projection` (clés de premier niveau gardées). |
| `timeout_s` | non (celui du connecteur) | Délai propre à la fonction, en secondes, de même type et mêmes bornes que celui du connecteur, qu'il remplace pour chacun de ses appels (chaque page d'une lecture paginée) : plus court (une page qui peut rester pendue) ou plus long (une réponse d'IA synchrone de plusieurs minutes), jamais égal (la fabrique refuse, règle 11). |
| `async` | non | La fonction soumet un travail relevé plus tard : `collect` (la relève), `job_id` (`from`, `to`), `within_s` ou `no_deadline` ; voir « Travail asynchrone ». |
| `background` | non | `true` : le tiers répond en minutes, l'hôte exécute la fonction en tâche de fond et rend aussitôt un identifiant de travail ; exige un `timeout_s` propre ; voir « Fonction longue ». |
| `cost` | non | Ce que coûte un appel : `per` (`request`, `page` ou `item`), `quantity` (ce que coûte une requête, `request` et `page`), `items` et `times` (les listes comptées, `per: item`) ou `weights` (le poids des valeurs que liste chaque élément), `unit`, `settle` (la quantité réelle relue) ; voir « Coût d'un appel ». |
| `confirm` | si `sensitive` | `summary`, gabarit du résumé montré avant exécution (`Validate invoice {id}: irreversible.`). |

**Lire et agir.** Chaque connecteur à effet se partage en deux côtés : `<connecteur>` (lire et simuler, brouillon compris) et `<connecteur>_act` (tout ce qui engage ou détruit : envoi, corbeille, archive, déplacement). Le partage se lit sur `act`, fonction par fonction : une seule description, un seul compte, et l'hôte sert les fonctions `act` sous le nom `<connecteur>_act.<fonction>`, les autres sous `<connecteur>.<fonction>`. `class` dit ce que fait une fonction et si elle se confirme ; `act`, de quel côté elle est servie : un brouillon est une écriture (`write`) qui reste du côté lecture (`act: false`).

**Donnée personnelle** (écrit le 19/10) : `personal: true` sur une propriété de l'entrée, à toute profondeur (élément d'une liste, branche d'un `anyOf`, clés libres d'un objet par `additionalProperties`), dit que sa valeur désigne une personne (un courriel, un nom, une adresse) : l'hôte ne la journalise jamais, ni dans les arguments, ni dans la cible, ni dans un message d'erreur du tiers qui la recopie. Le mot passe tel quel dans le schéma de la sortie TypeScript, que le paquet de l'hôte sert et valide ; il ne change ni l'appel ni la validation. Le client Python n'en fait rien. Jamais sur la racine, jamais dans `output.schema`, toujours `true` (la fabrique refuse, règle 15). Il dit une nature de l'argument, vraie chez tous les hôtes ; réserver une fonction au serveur de l'hôte reste le choix de l'hôte, jamais celui de la description.

```yaml
input:
  type: object
  additionalProperties: false
  required: [email]
  properties:
    email: { type: string, personal: true }
```

**Délai par fonction** (décidé le 16/10, écrit le 19/10) : `timeout_s` sur une fonction remplace, pour elle seule, celui du connecteur, plus court ou plus long. La sortie TypeScript le porte en millisecondes (`timeoutMs` de la fonction, à côté de celui du connecteur) :

```yaml
connector:
  timeout_s: 120
functions:
  - name: get_company
    call: { method: GET, path: "/linkedin/company/{identifier}" }
    timeout_s: 60
```

**Retirer de la sortie** (décidé le 21/10 ; une adresse signée ne sort plus jamais vers l'agent) : `output.strip` liste des clés que la réponse perd avant d'atteindre l'agent, chacune par son chemin, des clés séparées par des points. Une entrée sans point est une clé de premier niveau, comme avant le 21/10 ; `call.recording` désigne la clé `recording` de l'objet `call` d'une réponse emballée.

```yaml
# Une téléphonie qui emballe sa réponse : { "call": { "id": 1, "recording": "<adresse signée>", … } }.
- name: get_call
  output:
    strip: [call.recording, call.voicemail]
    sample: { call: { id: 1, recording: "https://files.example.test/r.mp3", voicemail: "https://files.example.test/v.mp3" } }
# La liste des appels : chaque élément de `calls` est un appel, sans emballage.
- name: list_calls
  output: { items: calls, strip: [recording, voicemail] }
```

- Le chemin part de chaque élément de la liste quand `items` est déclaré, de la réponse entière sinon.
- Une liste rencontrée en chemin se traverse : le reste du chemin vaut pour chacun de ses éléments (`participants.recording`), listes de listes comprises ; une réponse qui est elle-même une liste, sans `items`, se traverse de même. Un segment n'est jamais un indice : `0` est une clé.
- Une valeur absente, nulle ou scalaire là où le chemin attend un objet n'a rien à retirer, sans erreur : un champ facultatif peut manquer (un appel sans messagerie n'a pas de `voicemail`). Une clé présente est retirée quelle que soit sa valeur, `null` comprise.
- `strip` s'applique avant `projection`, qui reste au premier niveau.
- Limite assumée : une clé qui contient elle-même un point ne se désigne pas.
- La fabrique refuse (règle 18, [fabrique](fabrique.md)) un chemin mal formé (segment vide, point en tête, en fin ou doublé : `strip_path_malformed`), déclaré deux fois (`strip_path_twice`), ou sous un autre chemin de la liste, qui le retire déjà en entier (`strip_path_overlaps`) ; le schéma refuse aussi une liste vide.
- **L'exemple de réponse** (`output.sample`, décidé le 21/10) : une réponse brute de l'API, inventée, exigée dès qu'un chemin de `strip` porte un point. La fabrique y juge chaque chemin de `strip` (règle 19) : un chemin désigne quelque chose s'il atteint sa clé dans au moins un élément de l'exemple, relatif à `items` et à travers les listes comme à l'exécution ; sinon elle refuse (`strip_path_absent` : une faute de frappe sur la dernière clé, un parent absent). Elle refuse aussi un chemin à points sans exemple (`strip_path_unsampled`) et un exemple sans chemin à points (`strip_sample_unused`) : il n'a pas d'autre usage, et un exemple sans usage vieillit en silence. Une clé de premier niveau seule ne l'exige pas.
- L'exemple est **une garde, pas un contrat de réponse** : ni validation à l'exécution, ni documentation de l'API, ni source de types. Il ne sort ni dans la sortie TypeScript ni dans les données Python : l'hôte ne le voit jamais.
- Il ne contient que des **valeurs inventées**, jamais recopiées d'une réponse réelle ni d'une documentation publique : adresses en `example.test`, identifiants manifestement factices (`c-0`). La fabrique refuse (`strip_sample_foreign_address`) toute adresse (`scheme://hôte`, courriel) hors des domaines réservés aux tests (`.test`, `.example`, `.invalid`, `localhost`, `example.com`, `.net`, `.org`), et des identifiants dans une adresse (un nom et un mot de passe avant l'hôte) ; son message dit où, jamais la valeur. Un jeton ne se reconnaît pas à sa forme générale : la relecture reste la garde.
- Les cas communs (`connectors/_cases/strip.yaml`, [fabrique](fabrique.md)) disent, sur des réponses simulées, ce que l'agent reçoit.

**Le corps entier** (décidé par le superviseur le 2026-10-22, règle 20 de la [fabrique](fabrique.md)) : `call.body` nomme un argument au lieu d'associer des noms côté API à des arguments, quand le tiers prend pour corps un objet entier que l'agent compose (un contact, les réglages d'une campagne, une étape de séquence). La forme est celle d'une référence d'argument partout ailleurs dans le format (`request_param`, `cost.items`, `job_id.to`) : un nom, là où une table associerait des noms. Un corps est ainsi une table ou un argument, jamais les deux : le schéma ne connaît qu'une clé `body`.

```yaml
input:
  type: object
  additionalProperties: false
  required: [campaign_id, lead]
  properties:
    campaign_id: { type: string }
    lead:
      type: object
      additionalProperties: false
      required: [email]
      properties:
        email: { type: string, personal: true }
        first_name: { type: string }
call:
  method: POST
  path: "/campaigns/{campaign_id}/leads"
  body: lead
```

- **Ce qui part** : l'objet validé contre le schéma d'entrée, tel quel, en corps JSON (`Content-Type: application/json`, comme un corps en table). Une propriété absente ne part pas, une propriété `null` part `null`, comme une entrée d'une table ; aucune clé n'est ajoutée, renommée ni retirée.
- **L'argument est un objet strict** (`body_argument_not_strict`) : `type: object` (pas `[object, "null"]`), `additionalProperties: false`, au moins une propriété déclarée, sans `patternProperties`. Ce que l'agent peut mettre au corps est dit clé par clé, jamais un sac libre que le tiers lirait à sa façon ; une propriété de l'objet reste libre de sa propre forme (une table de variables, `additionalProperties: { type: string }`).
- **Ou à clés libres en texte** (décidé par Alexis le 2026-10-22) : à la racine de l'argument seulement, `additionalProperties` peut valoir, au lieu de `false`, exactement `{ type: string, personal: true }`, quand le tiers prend au premier niveau du corps, à côté de ses champs connus, des clés que l'utilisateur crée (les variables d'un lead, les champs personnalisés d'un contact). Les clés déclarées gardent leur schéma ; toute autre clé est un texte, et une donnée personnelle (« Donnée personnelle ») : l'hôte ne journalise pas sa valeur, par prudence, puisque rien ne dit ce qu'elle porte. Une clé libre qui n'est pas un texte (nombre, `null`, objet, liste) est refusée par le schéma d'entrée, avant tout envoi ; elle part, sinon, dans le même corps JSON que les clés déclarées, telle quelle. Toute autre forme reste `body_argument_not_strict` : `true`, un autre type (nombre, objet, `[string, "null"]`), un schéma sans `personal` ou avec `personal: false`, un mot de plus (`maxLength`, `description`), des clés libres avec `patternProperties` ou sans propriété déclarée. `maxLength` n'est pas admis : la source qui a motivé la forme (l'OpenAPI de lemlist, `additionalProperties: { type: string }`) ne borne pas la valeur, et une forme sans besoin serait à tenir des deux côtés ; il s'ajoutera avec la description qui en aura un. Un objet imbriqué dans l'argument garde sa forme libre, comme avant.

```yaml
contact:
  type: object
  additionalProperties: { type: string, personal: true }
  required: [email]
  properties:
    email: { type: string, personal: true }
    score: { type: integer, minimum: 0 }
```

- **Ou à clés libres à valeur simple** (décidé par Alexis le 2026-10-22) : au même endroit, `additionalProperties` peut valoir exactement `{ type: [string, number, boolean], personal: true }`, quand le tiers type les champs que l'utilisateur crée (les champs personnalisés d'un CRM, nombre, vrai/faux ou date). Chaque description choisit l'un des deux genres. Toute clé libre est alors un texte, un nombre ou un vrai/faux, et une donnée personnelle, quel que soit son type ; `null`, un objet ou une liste sont refusés par le schéma d'entrée, avant tout envoi ; une date est un texte. `number` et pas `integer` : un champ nombre du tiers prend une décimale, et JSON ne distingue pas `2` de `2.0`. Les trois types s'écrivent dans cet ordre : une seule écriture, que la fabrique et oto-core comparent telle quelle ; un autre ordre, un type de plus ou de moins (`integer`, `"null"`, `object`), un schéma sans `personal` ou un mot de plus (`maxLength`, toujours non admis) restent `body_argument_not_strict`.

```yaml
account:
  type: object
  additionalProperties: { type: [string, number, boolean], personal: true }
  required: [name]
  properties:
    name: { type: string }
```

- **Il est requis** (`body_argument_optional`) : le corps n'est jamais absent ; un objet vide, si le schéma l'admet, part `{}`. Il est **déclaré** dans l'entrée (`body_argument_unknown`).
- **Il ne va nulle part ailleurs** (`body_argument_elsewhere`) : ni chemin, ni query, ni en-tête, ni partie fichier ; les autres arguments gardent leurs places (chemin, query, en-têtes). `encode` ne le nomme pas (`body_argument_encoded`) : il part en objet, pas en chaîne.
- **Rien d'autre n'entre au corps** (`body_argument_not_alone`) : ni constante de corps (`constants.body`), ni partie fichier (`files`, dont le corps est multipart) ; ce que l'hôte envoie est l'objet validé, exactement.
- **La méthode envoie un corps** (`body_argument_method`) : jamais `GET` ; `DELETE` en porte un, comme un corps en table.
- **Pas de pagination** (`body_argument_paginated`) : une recherche paginée en `POST` porte son curseur dans son corps, que cette forme ne sait pas écrire sans changer l'objet de l'agent ; un curseur en query à côté d'un corps entier n'a aucun cas connu. À rouvrir avec une description qui en a besoin.
- **Ce qui ne change pas** : les exemples se valident contre l'entrée comme tout exemple (un objet hors schéma est refusé par la fabrique) ; `class`, `act` et `confirm` sont indépendants du corps (`confirm.summary` peut citer l'argument, que l'hôte écrit en JSON) ; `personal` marque une propriété de l'objet comme toute propriété. Tout argument a une place (règle 1) : celle de l'argument du corps entier est le corps.
- La fabrique refuse ce qui précède avec ces codes, dans cet ordre, les mêmes que ceux d'oto-core ; les cas communs (`connectors/_cases/body.yaml`, [fabrique](fabrique.md)) disent, sur des appels simulés, la requête envoyée, les entrées refusées avant tout envoi et les fonctions refusées.

**Le corps emboîté** (décidé par Alexis le 2026-10-26, règle 22 de la [fabrique](fabrique.md)) : dans un corps en table, la valeur d'une clé est un argument ou une table de même forme, à toute profondeur, quand le tiers prend les arguments sous une clé du corps : une enveloppe (`{"data": {…}}`), les variables d'une requête GraphQL (`{"query": "…", "variables": {…}}`), une ressource typée (`{"data": {"type": …, "attributes": {…}}}`). La table s'écrit dans la forme du corps envoyé, comme `constants.body` ; une clé est une clé, jamais un chemin : un point n'y est qu'un caractère.

```yaml
# Une API GraphQL : le texte de la requête est constant, les arguments sont ses variables.
input:
  type: object
  additionalProperties: false
  required: [issue_id]
  properties:
    issue_id: { type: string }
    title: { type: string }
    team_id: { type: string }
call:
  method: POST
  path: /graphql
  body: { variables: { id: issue_id, input: { title: title, teamId: team_id } } }
  constants:
    body: { query: "mutation UpdateIssue($id: String!, $input: IssueInput!) { updateIssue(id: $id, input: $input) { ok } }" }
```

- **Ce qui part** : la constante du corps, puis chaque argument donné posé à son chemin, les objets parents créés au besoin : `{"query": "mutation …", "variables": {"id": "i-1", "input": {"title": "Spring"}}}`. Un argument absent ne part pas et ne crée aucun parent (sans `title` ni `team_id`, `variables` ne porte que `id`) ; un `null` part `null` ; `encode` s'applique à l'argument avant qu'il soit posé, comme au premier niveau.
- **Constante et table ne se rejoignent que par des objets** (`body_key_twice`) : sous un même parent, elles portent des clés distinctes, sauf une clé qui est un objet des deux côtés, jugée alors au niveau en dessous. Refusés : un argument sur une clé constante (`data.format` constant et argument), un argument à la place d'un objet constant (`data` argument, `data.format` constant), une table sous une constante qui n'est pas un objet. La règle vaut au premier niveau : `draft` à la fois constant et argument est refusé avec ce code.
- **Une table emboîtée porte au moins une entrée** (`body_nested_empty`) : vide, elle ne poserait rien. Une table de premier niveau vide reste l'absence de corps en table.
- **Pas de table emboîtée dans un corps multipart** (`body_nested_multipart`) : ses parties sont des textes, une par clé de premier niveau.
- **La pagination sous une clé emboîtée** : `request_param` nomme un argument, où qu'il soit placé ; chaque page se compose comme la première, le curseur à la place de l'argument. `next`, `more` et `total` sont des chemins pointés de la réponse : `body: { variables: { first: first, after: after } }`, `request_param: after`, `next: data.issues.pageInfo.endCursor`, `more: data.issues.pageInfo.hasNextPage`.
- **Ce qu'elle ne dit pas**, qui reste au client : une requête GraphQL bâtie selon les arguments donnés (un champ demandé seulement quand un argument le dit) ; un argument emballé dans une liste (`filterGroups: [{filters}]`) ; une valeur dérivée d'un argument (un identifiant tiré d'un nom, une échéance complétée) ; un verbe choisi par un argument (`PATCH` ou `PUT`).
- **Sortie TypeScript** : la table telle quelle (`RequestSpec.body`, de type `BodyMap`). Un paquet d'hôte qui n'attend qu'une table plate la refuse à la déclaration (une valeur qui n'est pas un nom d'argument : « request places [object Object], which the schema does not declare »), au lieu d'envoyer un corps faux.
- La fabrique refuse ce qui précède avec ces codes, dans cet ordre, les mêmes que ceux d'oto-core ; les cas communs (`connectors/_cases/nested_body.yaml`, [fabrique](fabrique.md)) disent, sur des appels simulés, la requête envoyée (pagination comprise), les entrées refusées avant tout envoi et les fonctions refusées.

### Fichiers

Décidé le 16/10, écrit le 19/10 pour l'entrée : une fonction qui envoie un fichier à un tiers ne reçoit jamais ses octets de l'agent, mais l'identifiant d'un fichier de l'hôte, un fichier en transit de la personne qui appelle (oto-pkg : docs/conception/fichiers-et-stockage.md, « Fichier en transit »). `call.files` associe un nom de partie à l'argument qui porte cet identifiant, et fait partir le corps en `multipart/form-data` :

```yaml
input:
  type: object
  additionalProperties: false
  required: [company_id, parent_folder_id, file]
  properties:
    company_id: { type: integer }
    parent_folder_id: { type: integer }
    file: { type: string, format: uuid, description: "Id of a transit file of yours: the file to upload." }
    name: { type: string, maxLength: 255 }
call:
  method: POST
  path: "/companies/{company_id}/dms/files"
  body: { parent_folder_id: parent_folder_id, name: name }
  files: { file: file }
```

- Chaque entrée de `body` et chaque constante de corps devient une partie texte (un texte tel quel, un nombre ou un booléen écrit, le reste en JSON) ; chaque entrée de `files`, une partie fichier, au nom et au type du fichier en transit, que l'agent ne fournit pas. Un argument absent ne part pas.
- L'hôte lit le fichier sous l'identité de l'appelant : un fichier en transit de l'appelant, ou un fichier joint à une page qu'il lit, son lien `/f/<id>` (oto-pkg : docs/conception/connecteurs-et-comptes.md, « Fichiers envoyés à un tiers »). Un identifiant inconnu, échu, d'une autre personne ou d'une page qu'il ne lit pas est refusé de la même façon qu'un fichier inconnu, sans dire pourquoi. Le contenu n'est jamais rendu à l'agent ni écrit au journal.
- Un fichier joint à une page n'est jamais consommé : il vit avec sa page. Après un envoi réussi, l'hôte consomme le fichier en transit (il l'efface) ; sur un refus du tiers ou un envoi ambigu (délai dépassé, 5xx), il ne le consomme pas, et le fichier reste à son auteur jusqu'à son échéance. Le texte servi d'un argument fichier dit les deux sortes : « Id of an audio file: a transit file of yours, or a file on a page you can read (from its link /f/<id>). », et celui de la fonction, quand il dit la consommation, dit qu'un fichier en transit est consommé une fois que le tiers l'accepte et qu'un fichier de page reste.
- La fabrique refuse (règle 14, [fabrique](fabrique.md)) : `files` sur une méthode qui n'envoie pas de corps (`GET`, `DELETE`) ou sur une fonction paginée ; un argument fichier qui n'est pas un texte (`type: string`) ou que `encode` nomme ; un nom de partie fichier qui est aussi une entrée ou une constante de `body`. L'argument va à un seul endroit (règle 1).
- Le type « fichier » est porté par la place de l'argument, `files`, pas par son schéma : l'entrée reste un JSON Schema 2020-12 standard, servi et validé tel quel (« Décisions et alternatives écartées »).

**Compatibilité.** `pennylane_firm` 1.1.0, la seule description qui déclare `call.files`, exige oto-core à partir de son commit 3fe2fa6 (fichiers envoyés en multipart, lus sous l'identité de l'appelant) : un hôte monte ensemble ses deux épingles, celle de ce dépôt et celle d'oto-core, jamais l'une sans l'autre. Les descriptions qui disent un fichier joint à une page (`mistral` 1.0.1, `lemlist` 1.2.2, `pennylane_firm` 1.1.1, `yousign` 1.1.1) exigent oto-core à partir de son commit 9e58c01 : un paquet plus ancien refuse ce fichier comme un fichier inconnu. Ce dépôt n'a pas de journal des versions : ce rappel en tient lieu.

**Un fichier rendu** (décidé le 16/10, forme décidée par Alexis le 21/10 ; premier pas du chantier « fichier », que suivent l'adresse unique, garder et l'origine). Une fonction dont la sortie est un fichier (un enregistrement d'appel, un export, un PDF) le déclare par `output.file`. L'agent n'en reçoit jamais les octets ni l'adresse : l'hôte d'oto 2 le range en fichier en transit de la personne qui appelle et rend son identifiant, que l'agent passe tel quel à une fonction qui prend un fichier (`call.files`) ; le client Python le rend à son consommateur, qui le range où il veut. Exemple directeur : l'enregistrement d'un appel, que relit une transcription.

```yaml
# Une téléphonie dont la fiche d'un appel porte l'adresse signée de son enregistrement (une heure).
- name: get_call_recording
  class: read
  description: >-
    Get the audio recording of one call as a file of yours, kept 24 hours:
    the answer gives its file id, to pass as is to a function that takes a
    file (a transcription). Never a link.
  input:
    type: object
    additionalProperties: false
    required: [call_id]
    properties:
      call_id: { type: integer, minimum: 0 }
  examples:
    - { title: The recording of one call, input: { call_id: 987654321 } }
  refusals:
    - { code: call_not_found, when: 404, message: "No call with this id." }
  call: { method: GET, path: "/v1/calls/{call_id}" }
  output:
    file:
      from: url                    # body, url, base64, base64url ou json
      path: call.recording         # le champ de la réponse JSON qui porte l'adresse
      types: { mp3: [audio/mpeg, audio/mp3] }
      name: { template: "call-{call_id}-recording.mp3" }

# Une téléphonie qui rend l'audio pour corps, derrière l'authentification du compte :
  call: { method: GET, path: "/recordings/{recording_id}/download" }
  output:
    file:
      from: body
      types: { wav: [audio/wav, audio/x-wav, audio/wave], mp3: [audio/mpeg] }
      name: { header: Content-Disposition, template: "recording-{recording_id}.wav" }

# Un service qui rend sa transcription en JSON : la branche `data.result` devient le fichier.
  call: { method: GET, path: "/transcriptions/{transcription_id}" }
  output:
    file:
      from: json
      path: data.result
      name: { template: "transcription-{transcription_id}.json" }
```

- `from`, où sont les octets : `body`, le corps de la réponse (une réponse binaire) ; `url`, une adresse que porte la réponse JSON au chemin pointé `path`, téléchargée aussitôt ; `base64` ou `base64url`, les octets encodés dans un champ de la réponse JSON, au chemin `path` ; `json`, la réponse JSON elle-même, ou sa branche au chemin `path`, facultatif. La réponse JSON qui porte l'adresse ou l'encodage ne sort jamais : ni rendue, ni journalisée.
- `from: json` (décidé par Alexis le 2026-10-22) : un résultat trop gros ou trop riche pour être rendu à l'agent (une transcription, un export) devient un fichier en transit, que l'agent passe à une autre fonction. Le fichier est la réponse entière, ou, sous `path`, sa branche, lue comme tout chemin d'un fichier rendu (des clés séparées par des points, un indice de liste en nombre : `pages.1` ; une liste n'est pas traversée, `pages.text` ne désigne rien), par le même code que `url` et `base64` de chaque côté. Il est écrit en JSON comme l'écrit l'hôte, `JSON.stringify` de ce que lit `JSON.parse` : sans espace, en UTF-8, un nombre lu en double (`1.0` s'écrit `1`, `1.5e16` `15000000000000000`, un entier au-delà de 2⁵³ arrondi), les clés qui sont des indices de tableau d'abord, une clé en double gardant sa dernière valeur ; la lib Python l'écrit à l'identique. Son type est `application/json` : `types` est refusé. Son nom est son gabarit seul, qui finit par `.json` : ni `header`, ni `name.path`. `max_bytes` va de 1 octet à 4 Mo (4 194 304, la borne d'une réponse JSON chez l'hôte d'oto 2), 4 Mo par défaut, et borne le fichier écrit, pas la réponse ; une réponse de plus de 4 Mo est refusée (`file_too_large`) avant d'être lue. Un chemin qui ne mène à rien, ou à une valeur nulle, une chaîne, une liste ou un objet vides (la réponse entière comprise) refuse le fichier (`file_missing`) : jamais un fichier vide ; `0` et `false` sont des fichiers. Une réponse qui n'est pas du JSON (`NaN` compris) est illisible (`file_unreadable`). `auth` n'a pas de sens, rien n'étant téléchargé ; `expect` vaut, la réponse étant du JSON. Comme tout fichier rendu, jamais sur une fonction asynchrone ni sur sa relève, mais bien sur une fonction longue (« Fonction longue »).
- `auth` (`from: url` seulement) : `none` par défaut, une adresse signée portant sa propre signature et ne recevant aucun secret ; `account`, l'authentification du compte, posée seulement si l'adresse est à la même origine (schéma, hôte, port) que `base_url` résolue, sinon l'appel est refusé sans rien télécharger : le secret ne part jamais vers un autre hôte que l'API du tiers.
- `types` : les extensions que la fonction peut rendre, chacune avec les types MIME que le tiers peut annoncer, le premier étant celui du fichier rangé. Une réponse dont le type annoncé (`Content-Type`, sans ses paramètres) n'est ni l'un des types MIME de l'extension retenue pour le nom, ni `application/octet-stream` ou `binary/octet-stream`, ni absent, est refusée : une page d'erreur HTML ou un JSON sous un 200 ne passe pas pour le fichier. Chez l'hôte, le type d'un fichier vient de l'extension de son nom ; chaque extension déclarée est donc un type du paquet d'oto 2, au même premier type MIME (vérifié par l'hôte à la déclaration), jamais un type qu'ouvre le lecteur propre à un hôte : une description partagée sert tous les hôtes.
- `name`, essayé dans cet ordre : `header` (un en-tête de la réponse ; `Content-Disposition` se lit selon la RFC 6266, `filename*` avant `filename`), `path` (un champ de la réponse JSON), puis `template`, exigé, un gabarit sur les arguments requis de l'entrée (`{call_id}`) qui finit par une extension de `types`. Le premier nom dont l'extension est déclarée l'emporte ; le gabarit en donne toujours un. Un nom se réduit à son dernier segment, sans caractère de contrôle, 255 caractères au plus.
- `max_bytes` : de 1 octet à 50 Mo (52 428 800, le plafond d'un fichier chez l'hôte d'oto 2), 50 Mo par défaut (4 Mo pour `from: json`, ci-dessus) ; un fichier vide est refusé. Un `Content-Length` au-delà fait refuser avant toute lecture ; sinon les octets se comptent à la lecture, arrêtée au premier qui passe la borne. Une réponse en base64 se lit jusqu'à la taille encodée de `max_bytes`, au-delà des 4 Mo d'une réponse JSON ordinaire.
- Délai : celui de la fonction (`timeout_s`) vaut pour chaque requête, le téléchargement d'une adresse compris, lecture du corps comprise. Durée : 24 heures, celle de tout fichier en transit chez l'hôte d'oto 2 ; la description ne la change pas (« Décisions et alternatives écartées »).
- L'adresse téléchargée (`from: url`) : `https` seul, sans identifiants, vers un hôte qui ne résout jamais vers une adresse interne, aucune redirection suivie ; elle n'apparaît dans aucun résultat, message ni journal.
- Refus, rien n'étant gardé : champ d'adresse ou d'encodage absent ou vide, ou branche JSON absente ou vide (le tiers n'a pas de fichier), téléchargement refusé (statut hors 2xx : une adresse expirée se relit en rappelant la fonction), trop gros, type annoncé refusé, encodage illisible, délai dépassé, adresse d'une autre origine sous `auth: account`. Les refus de la fonction et la table d'erreurs valent pour l'appel à l'API, comme d'habitude. Le vocabulaire de chaque côté est dans sa conception : oto-pkg : docs/conception/connecteurs-et-comptes.md, « Fichiers rendus par un tiers » ; [fabrique](fabrique.md), « Un fichier dans le client Python ».
- La fabrique refuse (règle 17, [fabrique](fabrique.md)) : `output.file` avec `items`, `strip`, `projection` ou `schema` (`file_output_not_alone`) ; sur une fonction paginée, asynchrone ou relève d'un travail asynchrone, mais pas sur une fonction longue (`background`, décidé par Alexis le 2026-10-22), dont le fichier vient du même appel ; `path` absent avec `url`, `base64` ou `base64url`, ou présent avec `body`, comme `name.path` ; `auth` hors `from: url` (`file_auth_not_url`) ; avec `from: json`, `types` (`file_json_types`), un nom autre que le gabarit seul fini par `.json` (`file_json_name`), `max_bytes` au-delà de 4 Mo (`file_json_max_bytes`) ; `header` avec un `from` en base64 ; un gabarit qui cite autre chose qu'un argument requis de l'entrée ou qui ne finit pas par une extension déclarée ; une extension hors de 1 à 16 minuscules ou chiffres ; un type MIME mal formé, à paramètres, ou qu'un navigateur rend en page ou exécute (`text/html`, `image/svg+xml`, XML, JavaScript) ; `max_bytes` hors bornes ; `expect` avec `from: body`, qui n'a pas de JSON. Les cinq codes, les mêmes des deux côtés, sont jugés avant les autres refus de la règle, dans l'ordre où ils sont cités ; les cas communs (`connectors/_cases/file.yaml`) portent une fonction refusée pour chacun.

Décidé le 16/10, pas encore écrit : un corps brut, le fichier seul pour corps (téléversement de média). Aucune description ne l'attend encore (« Questions ouvertes »).

### Signal de refus du service

La description dit comment le service signale qu'il refuse la clé du compte ou que ses crédits sont épuisés, pour que l'hôte marque le compte et lève la marque au premier appel réussi. Une entrée de `errors`, ou un refus d'une fonction dont `when` est un statut, porte :
- `marks_account` : `credential_rejected` (le service refuse la clé ou le jeton du compte : clé invalide ou révoquée, session déconnectée, jeton révoqué) ou `quota_exhausted` (crédits ou quota de l'offre épuisés) ;
- `body`, facultatif : une condition sur le corps JSON de la réponse, sur la valeur au chemin pointé `path` (un indice de liste en chiffres : `errors.0.extensions.code`), par un seul opérateur, `equals` ou `contains`, jamais les deux (le schéma refuse). `equals` : la valeur est égale à l'une des valeurs listées (texte, entier ou booléen), de même type et exacte (`190` n'est pas `"190"`, un texte garde sa casse). `contains` (décidé le 2026-10-21) : la valeur est un texte qui contient l'un des textes listés, où qu'il soit, dans un mot compris, la casse à part : les deux côtés sont mis en minuscules par la casse Unicode par défaut, sans locale (`toLowerCase()` en JavaScript, `str.lower()` en Python, pas `casefold`, qui replierait aussi `ß` en `ss`). Une valeur absente, nulle, un nombre, un booléen, une liste ou un objet ne contient rien, ni un corps qui n'est pas du JSON ; un texte vide ne se déclare pas (le schéma exige des textes non vides, distincts, au moins un). L'entrée ne vaut que si la condition tient ; sinon l'hôte essaie l'entrée suivante du même statut.

Seul ce qui est déclaré marque : aucune entrée ne marque par défaut, un 401 compris. Une condition sur le corps dit un refus que le statut ne distingue pas : une erreur GraphQL sous un 200, un code d'erreur sous un 400.

```yaml
errors:
  - { status: 400, body: { path: error.code, equals: [190, 102] }, code: authorization_expired, retryable: false,
      marks_account: credential_rejected, message: "Meta no longer accepts this authorization (Graph error code 190 or 102): reconnect the account." }
  - { status: 400, code: invalid_request, retryable: false, message: "Meta rejected the request: check the ids, fields and parameters." }
  - { status: 401, code: authorization_expired, retryable: false, marks_account: credential_rejected, message: "…" }
  # une erreur GraphQL sous un 200 :
  - { status: 200, body: { path: errors.0.extensions.code, equals: [UNAUTHENTICATED] }, code: key_refused, retryable: false,
      marks_account: credential_rejected, message: "…" }
  # un message qui n'est pas fixe (« You have insufficient credits », « Insufficient credits on this plan ») :
  - { status: 422, body: { path: error, contains: [insufficient credits] }, code: credits_exhausted,
      retryable: false, marks_account: quota_exhausted, message: "…" }
  - { status: 422, code: invalid_request, retryable: false, message: "…" }
```

`contains` dit un refus que le service écrit en phrase, dont `equals` ne saurait lister toutes les formes. Pour plusieurs chemins possibles du même message, une entrée par chemin (`apollo`). Les cas communs (`connectors/_cases/errors.yaml`, [fabrique](fabrique.md)) disent, réponse par réponse, l'entrée retenue.

La fabrique refuse (règle 10, [fabrique](fabrique.md)) : `body` ou `marks_account` sur un refus dont `when` est une condition en texte, que l'hôte ne sait pas évaluer ; un statut 2xx sans condition sur le corps, qui ferait de chaque succès un refus ; `credential_rejected` sur un 403 sans condition (un droit manquant n'est pas une clé refusée) et `quota_exhausted` sur un 429 sans condition (un débit dépassé n'est pas un crédit épuisé) ; une entrée qui marque et se dit rejouable ; une entrée à condition placée, dans sa table, après une entrée sans condition qui partage un de ses statuts, et qui ne serait donc jamais lue.

Déclarent `marks_account: credential_rejected` sur leur 401, que leur table dit déjà clé ou jeton refusé : `affinity`, `claap`, `fod`, `klaviyo`, `mailpool`, `modjo`, `nextmotion`, `notion`, `pappers`, `pennylane_firm`, `sivan`, `typeform`, `wttj_ats`, `yousign`, `granola`, `attio`, `hunter`, `dropcontact`, `linear` (qui marque aussi le code GraphQL `AUTHENTICATION_ERROR` sous un 200, un 400 ou un 401), `linkedin_unipile` (session LinkedIn déconnectée, une clé refusée pour ce compte) et `meta_ads`, qui marque aussi les codes Graph 190 et 102 sous un 400 (ils remplacent le refus en texte que ses fonctions portaient). `fullenrich` ne marque son 401 que sous le code `error.api.key` (« Unknown api key ») : les deux autres codes documentés de son 401 disent un en-tête absent ou sans `Bearer`, une faute de l'appel et non de la clé. Il est le premier à déclarer `quota_exhausted` et une condition sous un 200 : le statut `CREDITS_INSUFFICIENT` d'un travail, sous un 200 ou un 402 ; un 402 sans ce statut ne marque rien. Ne marquent rien, faute de certitude : `aircall`, `amplitude`, `pennylane` et `sellsy`, dont la même entrée couvre 401 et 403 ; le 402 de `sellsy` (« quota de l'offre atteint pour cette ressource », pas un crédit du compte) et le 403 de `pappers` (crédits épuisés ou droit manquant, que le statut ne distingue pas) ; le 401 de `microsoft_app` (`oauth2_client_credentials`, dont l'hôte renouvelle le jeton) ; les codes 4, 17, 32, 613 et 80000 à 80014 de `meta_ads` (des débits). Les connecteurs `oauth2_user` ne déclarent rien : leur 401 relève du renouvellement du consentement par l'hôte. `mistral`, dont la clé est celle de l'hôte (`holder: host`), marque son 401 (`credential_rejected`) et son 402, un blocage de facturation de l'organisation Mistral (`quota_exhausted`) : la marque vaut pour un compte sans champ à lui, et l'hôte dit alors de demander à qui fait tourner l'application (oto-pkg : docs/conception/connecteurs-et-comptes.md, « Le refus nommé »). `amplemarket` marque son 402 sous le code `insufficient_credits` (`_errors.0.code`, le seul 402 de sa référence) en `quota_exhausted`, et ne marque pas son 401 : le seul code que sa référence lui donne, `unauthorized`, dit une clé invalide ou un droit manquant de l'utilisateur, que le statut ne distingue pas, et marquer bloquerait un compte sain (décision du mainteneur du 2026-10-23).

### Sonde à solde

La sonde d'un compte payant lit aussi son solde quand l'API du service le permet. Une sonde qui ne teste que l'autorisation répond « sain » sur un compte à zéro : la clé vaut, l'appel réussit. Lire un solde n'est pas le vérifier : `balance` dit où le lire et sous quel seuil la sonde n'est pas saine.

```yaml
probe: { function: get_account, balance: { path: credits.remaining, min: 1, unit: credits } }
```

- `path` : chemin pointé du solde dans la réponse de la fonction de sonde, un indice de liste en chiffres (`accounts.0.balance`) ; chaque segment est non vide, sans espace.
- `min` : le seuil, un nombre positif ou nul. Un solde égal ou supérieur est sain ; sous le seuil, absent ou qui n'est pas un nombre JSON (un texte `"12"` compris), la sonde n'est pas saine : un solde illisible ne passe jamais pour sain.
- `unit` : ce que compte le solde, tel que l'éditeur le nomme (`credits`, `requests`, `EUR`), rendu avec la valeur et le seuil.

On ne paie pas pour savoir si l'on peut payer : la fonction d'une sonde à solde ne déclare pas de `cost` (la fabrique refuse, règle 5), et le commentaire du fichier cite la source qui établit que l'appel de solde est gratuit et le chemin où le lire. Un solde qui se calcule (crédits de l'offre moins ceux consommés, plus un crédit prépayé) ne se dit pas : `path` lit une seule valeur. Sans source qui établisse le chemin et la gratuité, le fichier ne déclare pas de solde.

`hunter` est la première à déclarer un solde, `dropcontact` la deuxième : sa sonde, `check_credits`, un contact vide que Dropcontact ne facture pas (« Credits » de sa référence, relue le 2026-10-24), lit `credits_left`, saine à un crédit ou plus, en `credits`. Celle de `hunter` : sa sonde, `account_info`, gratuite (« This call is free », Account Information), lit les recherches restantes de la période, `data.requests.searches.remaining` (la référence dit de lire `remaining` ; `available` compte aussi les packs et ne baisse pas), saine à une recherche ou plus, en `searches`. Écartés au relevé du 2026-10-19, faute de source qui établisse un appel gratuit et un chemin unique : `pappers` (son suivi de crédits rend les crédits de l'offre, ceux consommés et le prépayé restant, sans solde en une valeur, et la référence ne dit pas l'appel gratuit) ; `affinity` (le quota mensuel du compte se lit à une route que la référence v1 dit exemptée de ce quota, mais la description ne la porte pas, la route v2 qu'appelle le client n'est pas dite exemptée, et la valeur rendue pour une offre sans limite n'est pas documentée) ; `sellsy` (le quota restant ne se lit que dans des en-têtes de réponse) ; `claap` (quota d'enregistrement de l'offre, sans lecture) ; `mailpool` (des actions facturées en crédits, sans lecture de solde ni dans son client ni dans le code d'oto 1). Les autres connecteurs décrits n'ont aucune lecture de solde, ni dans leur client, ni dans le code d'oto 1, ni dans leur description, ou signent avec la clé de l'hôte (`linkedin_unipile`).

### Coût d'un appel

`cost` dit ce que coûte un appel, en deux temps : avant lui, son pire cas, calculé sur ses seuls arguments ; après lui, la quantité réelle, relue dans sa réponse. Un service de facturation réserve le pire cas avant l'appel et règle la quantité réelle après. La description ne dit ni prix ni solde : des quantités, dans l'unité de l'éditeur.

```yaml
# Un lot facturé au champ demandé pour chaque contact, réglé au champ trouvé.
cost:
  per: item
  items: contacts                  # la liste dont chaque élément compte
  times: fields                    # la liste dont la taille multiplie (facultative)
  unit: fields                     # ce que comptent le pire cas et la quantité réglée
  settle: { path: fields_found }   # la quantité réelle, dans la réponse
```

- `per` : `request` ou `page`, `quantity` unités par requête envoyée, une sans elle ; `item`, une par élément de la liste `items`, fois la taille de la liste `times`.
- `quantity` (`request` et `page` seulement, décidé le 2026-10-21) : ce que coûte une requête, dans `unit`, un entier de deux ou plus ; absente, une. Une requête que l'éditeur facture plusieurs unités (une page Maps de `serper`, 3 crédits) déclare sa quantité, pour que le pire cas déclaré ne soit jamais sous le réel. Le schéma refuse `quantity: 1`, qui ne dirait rien (comme le délai d'une fonction égal à celui du connecteur, règle 11), une quantité sur `per: item`, qui compte ses éléments par `times` ou `weights`, et une quantité sans `unit` : trois requêtes par requête ne voudraient rien dire.
- `items` et `times` (`per: item` seulement, `items` exigé) : deux arguments distincts de l'entrée, des listes (`type: array`) requises, d'au moins un élément (`minItems` d'un ou plus).
- `weights` (`per: item` seulement, à la place de `times`) : le poids d'une valeur. `field` nomme un champ de chaque élément de `items`, une liste de valeurs ; `values` donne à chaque valeur admise son poids, un entier d'un ou plus, dans `unit`. Chaque élément compte la somme des poids des valeurs qu'il liste : un prix par genre de champ, que l'éditeur publie, et une liste de champs propre à chaque élément.

```yaml
# Une page Maps facturée 3 crédits, réglée aux crédits que dit la réponse (serper.search_maps).
cost: { per: request, quantity: 3, unit: credits, settle: { path: credits } }
```

```yaml
# Un lot facturé en crédits à la valeur trouvée, à un prix par champ, réglé aux crédits consommés
# (fullenrich.submit, barème public relevé le 2026-10-19).
cost:
  per: item
  items: contacts
  weights:
    field: enrich_fields           # dans chaque contact, les champs demandés
    values: { contact.work_emails: 1, contact.personal_emails: 3, contact.phones: 10 }
  unit: credits
  settle: { path: cost.credits }   # lu dans les réponses de la relève
```

  Le champ est, dans chaque élément, une liste requise d'au moins une valeur, sans doublon (`uniqueItems: true`), dont les valeurs admises (`items.enum`) sont exactement les clés de `values` (règle 16) : une valeur sans poids est refusée par le schéma d'entrée, que l'hôte valide avant l'appel, jamais comptée pour rien ; un poids sans valeur admise ne compterait jamais et est refusé de même. Le calcul refuse aussi, sans repli, une valeur sans poids qui lui parviendrait d'un appel non validé. Le barème est celui que publie l'éditeur, cité avec sa date dans le fichier : une offre sur mesure qui coûte plus est réglée telle quelle et signalée (« Quantité au-dessus du pire cas »).
- `unit` : ce que comptent le pire cas et la quantité réglée, tel que l'éditeur le nomme (`credits`, `contacts`, `fields`), comme l'unité d'un solde. Exigée par `per: item`, par `settle` et par `quantity` ; absente, des requêtes (`request`) ou des pages (`page`).
- `settle.path` : chemin pointé de la quantité réelle, de la même forme que `balance.path` (un indice de liste en chiffres, chaque segment non vide, sans espace).

La sémantique, que suit le service de facturation :
- **Pire cas**, avant l'appel. `request` et `page` comptent les requêtes que l'appel peut envoyer, fois `quantity` (une sans elle) : une requête, ou, pour une lecture paginée appelée avec `all_pages`, son `max_pages` borné par celui de la description (celui-ci quand l'appel n'en donne pas). `item` : la taille de `items` fois celle de `times`, une si `times` n'est pas déclaré ; avec `weights`, la somme, sur les éléments de `items`, des poids des valeurs que chacun liste.
- **Liste absente ou vide** : impossible. La fabrique exige `items` et `times` requis et d'au moins un élément, et le champ pesé requis dans chaque élément, d'au moins une valeur (règles 12 et 16), et l'hôte valide l'entrée avant l'appel : le pire cas est toujours un entier d'au moins 1, jamais deviné. Une liste vide ou absente laisserait l'éditeur appliquer son défaut (tous les champs, par exemple), qu'aucune description ne sait chiffrer.
- **Pagination** : elle multiplie le coût d'un `request` comme d'un `page`, chaque page étant une requête ; les deux comptent alors la même chose et ne diffèrent que par leur unité par défaut. Une fonction paginée ne déclare ni `per: item` ni `settle` (règle 12) : un lot ne se pagine pas, et une quantité lue dans une seule réponse ne dirait pas celle de l'appel.
- **Quantité réelle**, après un appel réussi. Avec `settle`, le nombre JSON fini, positif ou nul, lu au chemin dans la réponse JSON de l'appel telle que l'éditeur l'envoie, avant `output` ; pour une fonction asynchrone, dans les réponses de sa relève (« Travail asynchrone »). Sans `settle` : pour `request` et `page`, le nombre de requêtes effectivement envoyées, fois `quantity` ; pour `item`, le pire cas.
- **Quantité absente ou illisible** (chemin absent, valeur qui n'est pas un nombre JSON fini, un texte `"12"` compris, ou négative) : on règle le pire cas, et l'écart se signale. Refuser de régler laisserait ouverte une réservation que le service réglerait de toute façon au montant réservé, à son échéance, alors que l'éditeur a pu facturer. Comme un solde illisible ne passe jamais pour sain, une quantité illisible ne passe jamais pour nulle.
- **Nombre fini** : lu comme le lit un hôte JavaScript, un double ; un entier JSON au-delà de sa plage (lu `Infinity`) n'est pas fini, et une quantité ou un identifiant de travail qui en est un est illisible (lecture prudente, à confirmer : « Questions ouvertes »).
- **Quantité au-dessus du pire cas** : réglée telle quelle, l'éditeur l'a facturée ; la description sous-estime, et l'écart se signale.
- Un appel refusé (une erreur de la table, un contrôle) n'a pas de quantité réelle : sa réservation relève du service, libérée sur un refus net de l'éditeur, jamais sur un envoi ambigu (délai dépassé, 5xx).
- La fonction d'une sonde à solde ne déclare aucun coût, quel qu'il soit (règle 5).

Une description déclare un coût à l'élément et une quantité relue : `fullenrich.submit`, au poids de la valeur (ci-dessus), réglé aux crédits que rend sa relève (`cost.credits`). Sa référence facture chaque valeur trouvée, à un prix par champ (1 crédit un courriel professionnel, 3 un courriel personnel, 10 un mobile, « ratio » qui peut changer pour une offre sur mesure), les champs se demandent contact par contact, et le résultat rend les crédits consommés pour tout le travail. Écartés au relevé du 2026-10-19 : `pappers`, dont la référence chiffre les champs supplémentaires de la fiche à des prix différents d'un champ à l'autre, sans prix de base ni quantité dans la réponse (à revoir avec `weights`, « Questions ouvertes ») ; `mailpool`, qui facture des domaines et des boîtes à un prix lu par une autre fonction.

`amplemarket` compte ses lots à l'élément, sans quantité relue, aucune réponse ne rendant les crédits consommés : la validation d'emails en crédits d'email, un par email, au barème de sa référence ; l'enrichissement de personnes en leads, son barème (0,5 crédit d'email par personne trouvée, 1 par email révélé, 1 crédit de téléphone par numéro révélé, selon des drapeaux de la requête et non d'un champ de chaque élément) n'ayant ni une seule unité ni des poids entiers ; l'enrichissement de sociétés en sociétés, et les listes de leads en leads, à des prix que la référence ne publie pas. Le pire cas compte donc des leads ou des sociétés, pas des crédits : le prix d'un lead reste au service qui facture.

`dropcontact.submit` compte son lot au contact, en crédits, sans quantité relue : sa référence facture « au succès » 1 crédit par contact dont un email vérifié est rendu ou dont l'email envoyé est vérifié, et ses réponses ne rendent que le solde (`credits_left`), jamais les crédits consommés ; le pire cas, un crédit par contact, est réglé tel quel.

### Travail asynchrone

Une fonction qui soumet un travail dont le résultat se relève plus tard (un rapport, un téléchargement, une ingestion, un enrichissement en lot) le dit par `async` : la fonction de relève, et l'identifiant du travail qui les relie.

```yaml
- name: start_insights_report
  async: { collect: get_report_status, job_id: { from: report_run_id, to: report_run_id } }

# Un lot réglé à la relève :
- name: submit_enrichment
  cost: { per: item, items: contacts, unit: credits, settle: { path: cost.credits } }
  async: { collect: get_enrichment, job_id: { from: id, to: enrichment_id }, within_s: 600 }
```

- `collect` : une autre fonction de lecture du connecteur, appelée par `call`, qui n'est pas elle-même asynchrone, et dont `job_id.to` est le seul argument requis : la relève se fait avec l'identifiant du travail seul, par l'agent comme par l'hôte (règle 13).
- `job_id.from` : chemin pointé de l'identifiant dans la réponse de la soumission ; `job_id.to` : l'argument de la relève qui le reçoit.
- `within_s` : le délai de relève, en secondes après la soumission ; passé ce délai, le travail est fini et sa quantité lisible. Un entier de 1 à 86 400 : une réservation tient des crédits de l'organisation tant qu'elle court, et un travail plus long qu'un jour n'est plus un appel qu'un agent attend. Plus long que le délai de la soumission (règle 13). Exigé quand le coût se règle (`settle`), sauf `no_deadline`, facultatif sinon.
- `no_deadline: true` (décidé le 2026-10-19), exclusif de `within_s` : la référence de l'éditeur dit qu'un travail n'a pas d'échéance (« Jobs don't expire and there's no automatic timeout », FullEnrich), et le fichier le cite. Aucun délai n'est alors inventé : la réservation court jusqu'à la première quantité lisible dans les réponses de la relève, ou jusqu'à un plafond fixé par le moteur qui réserve, un réglage de ce moteur, le même pour tous ; au-delà, sans valeur lisible, on règle le pire cas, comme à une échéance, et le règlement le dit. Un règlement est idempotent : une quantité lue plus tard ne le modifie pas. Le plafond n'est pas dans la description, et sa valeur n'appartient pas au format : il dit combien de temps une organisation accepte de voir des crédits retenus, pas ce que fait l'éditeur. Écarté : laisser `within_s` absent sans rien dire, qui ne distingue pas une échéance oubliée d'une échéance qui n'existe pas.

Le règlement d'une fonction asynchrone se déclare sur la fonction qui soumet, et `cost.settle.path` se lit dans les réponses de sa relève. La réservation naît à la soumission, de ses arguments, et le même bloc dit où la régler ; la relève, appelée tant que le travail court, ne réserve rien et ne déclare ni `settle` ni pagination (règle 13). La première réponse de la relève de ce travail qui porte au chemin un nombre lisible le règle ; avant elle, une valeur absente veut dire « pas encore » ; à l'échéance, `within_s` après la soumission (ou au plafond du moteur qui réserve, sous `no_deadline`), sans valeur lisible, on règle le pire cas. Sans `settle`, la quantité se connaît dès la soumission et rien n'attend la relève. Pour un appel synchrone, l'échéance d'une réservation est le délai de la fonction (`timeout_s`, par requête), plus une marge que fixe le service.

Neuf paires décrites déclarent `async`, l'identifiant établi par le client Python ou par la description : `meta_ads.start_insights_report`, relevé par `get_report_status` (`report_run_id`, que lit `oto.tools.meta_ads`) ; `amplitude.request_cohort_download`, par `get_cohort_download_status` (`request_id`, que nomme `oto.tools.amplitude`) ; `fod.urban_start_regulation_ingestion`, par `urban_get_regulation_ingestion` (`idurba`, rendu dans l'état que donne la soumission, d'après sa description) ; `fullenrich.submit`, par `fetch` (`enrichment_id`, d'après l'OpenAPI v2 de FullEnrich et `oto.tools.fullenrich`) ; dans `amplemarket`, `start_person_enrichment` et `start_company_enrichment`, par `get_person_enrichment` et `get_company_enrichment` (`request_id`), `start_email_validation`, par `get_email_validation` (`validation_id`), et `create_lead_list`, par `get_lead_list` (`lead_list_id`), chacune rendant l'`id` du travail dans sa réponse 202, que lit `oto.tools.amplemarket` ; `dropcontact.submit`, par `fetch` (`request_id`, que lit `oto.tools.dropcontact`). Aucune ne déclare `within_s` : aucune source ne borne la durée de leur travail. Seule `fullenrich.submit` règle une quantité, sous `no_deadline`, sa référence disant qu'un travail n'expire pas. Les lignes d'un rapport Meta terminé se lisent par une troisième fonction, `get_report_insights`, que le format ne relie pas.

### Fonction longue

Décidé par Alexis le 2026-10-22 (oto-pkg : docs/conception/fonctions-longues.md). Un tiers qui répond en minutes à un appel unique et synchrone (une transcription audio : de 20 s à 5 min pour 30 min d'audio) le dit par `background: true` sur la fonction : un fait du tiers, comme `async`, pas un choix de l'hôte. L'hôte d'oto 2 exécute alors la fonction hors de la requête de l'assistant, en tâche de fond, et rend aussitôt un identifiant de travail, que relève sa fonction native `job.read` ; la réponse finale est exactement celle de l'appel synchrone (données, fichier rendu, refus), seul le moment change. `async` reste la forme d'un travail que tient le tiers (une soumission, puis une relève décrite) ; `background`, celle d'un appel long dont l'hôte tient l'attente.

```yaml
- name: transcribe_audio
  class: read
  call:
    method: POST
    path: /audio/transcriptions
    body: { language: language }
    files: { file: file }
  timeout_s: 300                   # le délai de l'appel lui-même, file non comprise
  background: true
  cost: { per: request, unit: seconds, settle: { path: usage.audio_seconds } }
  output:
    file: { from: json, name: { template: transcription.json } }
```

- `timeout_s` propre à la fonction est exigé, de 1 à 300 s : le délai de l'appel lui-même, l'attente en file non comprise ; la règle 11 vaut telle quelle, jamais égal à celui du connecteur. Celui du connecteur ne suffit pas : un délai est un plafond, pas une durée attendue, et la tâche de fond ne se déduit pas d'un délai long, que déclarent aussi des fonctions qui répondent en une seconde.
- La description ne dit rien de l'identifiant de travail : l'hôte ajoute au texte servi une phrase fixe sur la relève, et aucune description ne la réécrit.
- `class` et `act` valent tels quels, `write` et `act: true` compris. `confirm` se juge avant le lancement : le récapitulatif d'une fonction sensible est montré avant la mise en file. Le coût se règle à la fin du travail : `cost.settle.path` se lit sur la réponse finale, comme pour un appel synchrone ; c'est le moteur qui règle, la description ne dit rien de plus.
- `output.file` est admis (règle 17) : le fichier vient du même appel. `call.files` aussi : le fichier d'entrée n'est consommé qu'après un envoi réussi, comme pour un appel synchrone.
- La fabrique refuse (règle 21, [fabrique](fabrique.md)), dans cet ordre, chacun par son code : une fonction longue sans `timeout_s` propre (`background_no_timeout`) ; avec `async` (`background_async` : un travail que tient le tiers a sa relève décrite, et l'hôte n'a rien à tenir) ; relève d'un travail asynchrone (`background_collect` : une relève répond tout de suite) ; paginée (`background_paginated` : un appel, une réponse). Le schéma n'admet que `true`. Les cas communs (`connectors/_cases/background.yaml`) portent une fonction refusée pour chaque code, et des fonctions acceptées qui combinent `background` avec ce qu'il admet.
- Le client Python ignore `background` et appelle en synchrone : son consommateur choisit où l'appel tourne. La sortie TypeScript porte `background: true` sur la fonction (`ConnectorFunction.background`), à côté de `timeoutMs` ; les données Python (`oto/connectors/declared.py`) ne le portent pas.

Une description le déclare : `mistral.transcribe` (1.0.0, 2026-10-22), une transcription audio de 300 s au plus, son fichier rendu en JSON (« Les connecteurs décrits »).

### Le bloc `exposure`

L'exposition est une projection, pas une propriété de la fonction. `mode` vaut `per_action` (un outil `<namespace>_<name>` par fonction), `per_connector` (un outil par connecteur, l'action en paramètre) ou `via_call` (rien n'est exposé, le verbe d'appel lit le registre). Le défaut est `per_connector`, fixé par le consommateur ; `mode` le surcharge pour un connecteur, `tool` nomme l'outil unique en `per_connector`.

`exposure` et `modes` ne servent qu'à oto 1 : un hôte d'oto 2 sert ses fonctions par des outils fixes et dit qui fournit le compte par son propriétaire. Les deux blocs restent, marqués « oto 1 seulement », et partent quand oto 1 ne lira plus ce dépôt (décidé le 16/10).

Deux gardes de CI, décidées le 16/10 et écrites le 19/10 :

- **Un client, une description.** Un client de la lib est une entrée directe de `oto/tools/` (paquet ou module), ou un sous-paquet d'une famille (`google`, un paquet par service). Le code qu'une description couvre est le client du même nom que le connecteur, entier, ou ce que `described_by` de `connectors/clients.yaml` y rattache : un client entier d'un autre nom (les paquets Google à `gmail`, `google_drive`, `google_calendar` et `google_sheets`), ou seulement des fichiers d'un client, le reste du client n'étant alors le code d'aucun connecteur (`microsoft` : la surface fichiers, le consentement, ses droits et le transport commun, pas le courrier, l'agenda, Teams, OneNote, l'annuaire ni les cellules d'un classeur Excel ; `linkedin_unipile` : tout le client depuis sa 1.2.0, les méthodes que le format ne sait pas dire restant au client, nommées dans la description). Un client sans description est nommé dans `without_description`, avec une catégorie et sa raison. Trois catégories de principe admettent une entrée nouvelle : `not_a_service_client`, `not_describable` (le format ne sait pas le dire), `oto_service` (client d'un service d'oto) ; deux catégories en attente ne font que décroître : `before_the_rule` (antérieur à la règle du 05/10) et `not_described_yet`. `tests/test_clients_described.py` refuse un client qui n'est ni décrit ni nommé, et une entrée qui ne dit plus vrai (client ou fichier absent, connecteur sans description, exception dont le client a reçu sa description). Au 23/10, 111 exceptions : 6 `not_a_service_client` (utilitaires communs, nœud HTTP générique, Markdown, PDF, navigateur, code NAF), 7 `not_describable` (les six clients du paragraphe précédent, et un client sans API publique), 2 `oto_service`, 3 `not_described_yet` (ajoutés après la règle du 05/10 sans description) et 93 `before_the_rule` (`fullenrich` en est sorti le 2026-10-19, les clients décrits depuis à leur tour, `folk`, `slack`, `salesforce` et `origami` le 2026-10-22, `brevo` le 2026-10-23).
- **Gardes par commit.** `python -m fabrique.commits <avant> <après>`, lancé par le job `commits` de la CI avec l'historique entier, juge chaque commit nouveau d'une PR (de sa base à sa tête) ou d'un push de `main` (d'avant à après), un par un, contre son premier parent : le verdict ne dépend ni du regroupement des commits ni d'un rejeu. Un avant inconnu (premier push, `0000…`) ne fait juger que le commit de tête, et la sortie le dit ; un commit antérieur à `connectors/clients.yaml` (une PR ouverte avant la garde) est jugé avec celui de la tête ; un commit de fusion n'est jugé que sur ce qu'il change lui-même. Ni un tag ni un dispatch ne la lancent. Deux règles. *La version monte avec le code* : quand un commit change le code d'un connecteur (tout fichier de `connectors/<nom>/`, et son client tel que rattaché ci-dessus) qui existe avant et après lui, `connector.version` monte (semver), ou le commit porte dans son bloc de trailers, celui de `Changelog:`, la dispense `Version-dispense: <connecteur> — <raison>` (tiret cadratin), qui ne vaut que pour lui ; `Version-dispense: * — <raison>` dispense tous les connecteurs du commit, seulement s'il touche `connectors/connector.schema.json` ou `fabrique/` (une passe sur tout le format). Une version qui descend n'est jamais dispensée ; une dispense mal formée, hors du bloc de trailers, ou globale sans passe sur le format fait échouer le commit, dont le message d'échec donne la version cible ou la ligne à ajouter. La lib commune, la fabrique, la sortie générée, les tests et la version de la lib (`pyproject.toml`, `uv.lock`, le paquet npm, qui suivent le flux de publication) ne sont le code d'aucun connecteur : un commit de publication ne regarde aucun connecteur. Un correctif urgent passe par une dispense motivée. *Les exceptions en attente ne font que décroître* : un commit n'ajoute aucune entrée aux catégories `before_the_rule` et `not_described_yet` ; un client nouveau entre au format, ou dans une catégorie de principe avec son motif. Tests : `tests/test_commit_guards.py`. Une PR fusionnée par squash garde ses dispenses seulement si le message du commit fusionné les reprend en trailers.

## Décisions et alternatives écartées

- **Du code source dans l'un des deux langages** : écarté le 29/09. L'autre langage n'en serait qu'une traduction ; un fichier déclaratif se lit des deux côtés.
- **TOML** : écarté, illisible dès trois niveaux d'imbrication, qu'un schéma d'entrée dépasse souvent. **JSON seul** : écarté, sans commentaires et pénible pour une description sur plusieurs lignes.
- **Référencer la spec OpenAPI de l'éditeur** (`operation: getEstimates`) et n'ajouter que classe, refus, exemples et projection : non retenu à ce jour. Moins à écrire, mais chaque connecteur dépendrait de la qualité d'une spec tierce.
- **Un client ajouté à la lib sans description** : écarté le 2026-10-05. Tout client entre au format ; une fonction ou un client que le format ne sait pas dire est nommé, avec sa raison, dans « Les connecteurs décrits ».
- **L'outil MCP comme unité** (le modèle d'oto 1, où le nom de l'outil est le contrat et où Sellsy est servi par `sellsy_document(kind, op)`, quatre documents de vente fusionnés) : écarté. L'unité est la fonction ; l'outil, une projection. Cela répond au point « verbe `oto_call` ou outils dédiés » d'ADR 0070 §7.8 : les deux, par projection.
- **Un langage d'expressions pour les contrôles** (une formule « débits = crédits ») : écarté le 06/10. Des genres fermés et nommés (`equal_sums`, `non_empty`), chacun lié à un refus de la table, se lisent et s'exécutent pareil dans les deux langages ; un genre s'ajoute quand une description en a besoin.
- **Refus en texte libre** : écarté. Une table structurée (`code`, `when`, `message`) que la fabrique traduit en erreurs typées dans les deux langages.
- **Une seule version** : écarté. La version du fichier (semver) et celle de l'API tierce (en clair) sont deux champs.
- **Convertir les 713 outils existants, ou leur attribuer une classe** : écarté. La classe s'écrit à l'entrée d'un connecteur dans le format.
- **Un `type: file` dans le schéma d'entrée** (ou un mot-clé propre, `x-file`) : écarté le 2026-10-19. L'entrée est un JSON Schema 2020-12 servi et validé tel quel par un validateur standard, qui refuse un type inconnu ; un argument fichier y est un texte, l'identifiant, et c'est sa place, `call.files`, qui le dit fichier, comme `query` ou `body` disent où va un argument.
- **Les octets en base64 dans un argument, ou une adresse à télécharger** : écartés le 2026-10-16. Les octets passeraient par le contexte de l'agent ; une destination ne reçoit qu'un identifiant de fichier de l'hôte.
- **Rendre à l'agent l'adresse signée du tiers, ou les octets en base64**, pour qu'il les passe à la fonction suivante : écarté par Alexis le 2026-10-21. Une adresse signée fait des centaines de caractères, l'agent l'abîme en la recopiant (refus 400 ou 403 du tiers, sans cause lisible : c'est le correctif qu'oto 1 a dû écrire à la main), elle expire, elle donne le fichier à qui la détient et entrerait en clair au journal de l'appel suivant ; les octets passeraient par le contexte de l'agent. La sortie est un identifiant de fichier de l'hôte.
- **Un bloc `response` ou une sortie nommée à côté d'`output`** : écarté par Alexis le 2026-10-21. `output` dit déjà ce qui revient de l'appel ; un fichier en est une forme, exclusive des autres (`items`, `projection`), plutôt qu'un second canal à concilier avec eux.
- **Le type du fichier pris du `Content-Type` du tiers, ou une liste de types MIME seule** : écarté par Alexis le 2026-10-21. L'hôte d'oto 2 décide le type par l'extension du nom, jamais par ce qu'annonce l'expéditeur ; la description déclare donc des extensions, et le type annoncé ne sert qu'à refuser ce qui n'est manifestement pas le fichier.
- **Une durée de transit déclarée par la fonction** (`transit_hours`, plus longue que 24 h pour un export ou un enregistrement à transcrire) : écartée par Alexis le 2026-10-21. La durée est une règle de stockage et de quota de l'hôte, une seule pour tout fichier en transit, gardée en base, qu'un tiers ne connaît pas ; un enregistrement se transcrit dans l'heure, et un fichier à conserver plus longtemps se garde sur une page.
- **Des types réservés au transit, ou ouverts par un hôte** (`registerReaders`) pour qu'une fonction rende un audio : écartés par Alexis le 2026-10-21. Les types audio (`mp3`, `wav`, `m4a`, `ogg`) entrent dans les types du paquet d'oto 2, pour tout fichier : garder un fichier en transit le rend joint sans copie, un type admis en transit seulement ne se garderait pas, et un type ouvert par un hôte ne vaut pas pour une description partagée, qui les sert tous.
- **Un plafond au-delà de 50 Mo pour un enregistrement** : écarté par Alexis le 2026-10-21. Un WAV de téléphonie non compressé (8 kHz, 16 bits, mono) passe 50 Mo vers 55 minutes, un MP3 de téléphonie vers plusieurs heures ; aucun cas réel ne le dépasse, et le fichier se lit en mémoire. Au-delà, le refus `file_too_large`.
- **Suivre les redirections d'une adresse de téléchargement** (une adresse courte, un 302 vers le stockage du tiers) : écarté à l'étape 1 par Alexis le 2026-10-21. L'adresse directe suffit aux cas connus ; chaque saut serait une adresse de plus à garder, et l'authentification ne devrait pas le suivre. À rouvrir avec une description qui en a besoin.
- **Laisser à l'agent les adresses d'enregistrement d'`aircall`** (`list_calls`, `get_call`) : écarté par Alexis le 2026-10-21. `aircall` 1.1.0 les retire de ses lectures et rend l'audio par `get_call_recording` et `get_call_voicemail`, en sortie fichier ; `allo` 1.1.0 de même, son lien signé (`get_recording_link`) remplacé par `get_call_recording`.
- **Garder les descriptions en français** : écarté. Ce que lit l'agent est en anglais ; une description française se traduit à son entrée.
- **Un seul secret par compte, l'adresse ou la région dans un champ du credential** : écarté le 2026-10-08. Un compte garde tous ses champs ; une région ou une adresse est un réglage non secret, typé (liste fermée, motif, adresse libre gardée à l'exécution), cité par un gabarit, que l'écran de l'hôte propose et que l'exécution vérifie.
- **Un connecteur par région** (`typeform_eu`) : écarté le 2026-10-08 ; les fonctions et le contrat ne changent pas avec l'hôte.
- **`oauth2_user` renvoyé à du code écrit à la main, le jeton passé en `bearer`** : écarté le 2026-10-08. Le consentement (adresses, scopes, PKCE, renouvellement, rotation, identité) se décrit, et l'hôte l'exécute une fois pour tous.
- **L'identifiant et le secret du client OAuth dans `credential`** : écarté le 2026-10-08. Ils appartiennent à l'application (de l'hôte, ou de l'organisation qui pose la sienne), pas au compte d'une personne.

- **Une clé de corps en chemin pointé** (`"variables.input.teamId": team_id`) : écartée le 2026-10-26 pour le corps emboîté. Une table emboîtée a la forme du corps envoyé et celle de `constants.body` ; un chemin pointé demanderait une syntaxe, ses refus (segment vide, chemins qui se chevauchent) et une clé qui contient un point ne se dirait plus ; et un paquet d'hôte antérieur enverrait la clé pointée telle quelle, un corps faux, là où il refuse une table emboîtée à la déclaration.

## Sécurité et confidentialité

- Le fichier ne porte aucun secret : il nomme les champs du credential (`secret: true`) et `auth` y renvoie par leur nom ; un réglage n'est jamais un secret. Une clé passée en query (`in: query`) est admise : le tiers l'a voulue là et la voit de toute façon ; l'exécution la masque dans tout journal, adresse comprise. Le secret est fourni par le consommateur à chaque appel ; la lib n'en lit aucun (garde `tests/test_no_secret_read_guard.py`).
- Une adresse saisie par un admin (`url`, valeur de `from_token`) n'est suivie qu'en `https`, vers un hôte qui ne résout jamais vers une adresse interne, sans redirection ; le format le déclare, l'exécution le garde.
- `base_url` nomme la racine documentée de l'API de l'éditeur. Une coordonnée tirée du front d'un tiers (clé d'API publique, identifiant d'application) n'entre jamais dans un fichier (`docs/conventions.md`).
- Le dépôt est public : un connecteur dont l'accès appartient à un client, son propre back-office, n'a pas de description ici ; c'est un connecteur propre à son hôte.
- Un message de refus dit le fait, au plus une condition, jamais le nom d'un outil : la lib ne connaît pas les outils de l'appelant.
- Une adresse que rend un tiers pour télécharger un fichier (`output.file`, `from: url`) est un jeton porteur : consommée par l'exécution, gardée comme une adresse saisie (`https`, jamais un hôte interne, aucune redirection), jamais rendue, citée dans un message ni journalisée. L'authentification du compte ne la suit que sous `auth: account` et vers l'origine de l'API ; ni la lib ni la sortie TypeScript ne lisent le secret, que le consommateur fournit.
