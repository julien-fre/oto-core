# Format de description d'un connecteur

- **Statut** : validé par le mainteneur le 29/09/2026
- **Dernière révision** : 2026-10-19

## Résumé

Un connecteur partagé se décrit dans un fichier YAML, `connectors/<nom>/connector.yaml`, validé par `connectors/connector.schema.json` (JSON Schema 2020-12). L'unité du format est la fonction servie avec son appel : ce que l'agent voit (nom, description en anglais, schéma d'entrée strict, classe, exemples, refus nommés) et la requête derrière (méthode, chemin, répartition des arguments, pagination, sortie). Ce qui ne se décrit pas reste du code écrit à la main, référencé depuis le fichier. Le bloc `connector` dit aussi ce qu'est un compte : les champs de son credential, ses réglages non secrets (région, adresse), son authentification, consentement OAuth d'une personne compris, et, pour un compte rattaché chez un tiers qui héberge les comptes de ses utilisateurs, l'identité de ce compte et les champs que fournit l'hôte. La [fabrique](fabrique.md) en tire Python et TypeScript ; vingt-six connecteurs ont leur description, et tout client ajouté à la lib entre au format.

## Contexte

- La lib porte une centaine de clients Python écrits à la main. Au relevé du 29/09, le schéma d'un outil y vient de la signature et sa description de la docstring ; aucune classe n'est déclarée, aucun refus n'est nommé, la confirmation se fait au cas par cas.
- Le paquet d'oto 2 sert des fonctions qui déclarent classe, exemples, refus et résumé de confirmation. Elles ne sont pas des outils MCP : elles se trouvent, se lisent et s'appellent par les six outils figés du paquet (oto-pkg : docs/conception/connecteurs-et-comptes.md).
- Un connecteur partagé sert deux langages : Python pour la lib, TypeScript pour le paquet. Écrit deux fois à la main, il divergerait ; d'où une description unique.
- Relevé du 29/09 sur 114 connecteurs de la lib, par lecture du code et à seuil arbitraire : 54 enveloppes d'API REST, 44 REST avec logique, 16 hors format (3 navigateur, 7 données ouvertes ou base embarquée, 3 SDK, 2 traitement local, 1 asynchrone).
- Se décrit : authentification (clé, basique, client credentials, consentement d'une personne), réglages d'un compte, URL de base, verbe et chemin, répartition des arguments, constantes et en-têtes constants, encodage JSON d'un argument, schéma, table des erreurs et leur caractère rejouable, signal de refus du service (clé refusée, crédits épuisés, y compris sous un 200 ou un 400), délai d'un appel, par connecteur ou par fonction, contrôles simples avant l'appel et sur la réponse, projection de sortie, règle de coût, pagination, rythme maximal du tiers, sonde et solde d'un compte payant. Reste à la main : fusion de plusieurs appels, refus locaux que les contrôles déclarés ne disent pas, construction d'un mail, identité opérée.

## Objectifs et non-objectifs

- Une seule source par connecteur partagé, d'où sortent les deux langages.
- Le contrat vu de l'agent s'écrit une fois : classe, exemples validés, refus nommés, en anglais.
- Un fichier invalide est refusé avant toute génération.
- Ce qui ne se décrit pas reste possible, par une entrée `handwritten` dont le schéma, la classe et les refus restent déclaratifs.
- Hors objectif : convertir les connecteurs existants. Ils restent en Python tels quels ; seuls les nouveaux connecteurs partagés et ceux qu'oto 2 demande entrent au format, et un existant réclamé entre comme un nouveau.
- Hors objectif : décrire un connecteur propre à un hôte, écrit dans l'hôte au contrat du paquet (oto-pkg : docs/conception/connecteurs-et-comptes.md).
- Hors objectif : porter un secret, un compte ou une activation. Le fichier nomme les champs du credential et les réglages, et décrit le consentement ; garder, chiffrer, rafraîchir et résoudre relèvent de l'hôte.

## Conception

### Le fichier

- Un dossier par connecteur sous `connectors/` : son `connector.yaml` et, si besoin, son code écrit à la main dans les deux langages. `connector.name` est le nom du dossier.
- YAML, déclaré en version 1.2, validé par un schéma JSON 2020-12 que les deux langages savent lire. Le fichier porte en tête `# yaml-language-server: $schema=../connector.schema.json`.
- Trois blocs : `connector` (un par fichier), `functions` (au moins une), `exposure` (facultatif). Toute clé inconnue fait refuser le fichier.

### Le bloc `connector`

| Champ | Obligatoire | Sens |
|---|---|---|
| `name` | oui | Identifiant stable (`^[a-z][a-z0-9_]*$`), premier segment des outils. |
| `label` | oui | Nom affiché. |
| `namespace` | oui | Préfixe des outils exposés, souvent égal à `name`. |
| `version` | oui | Version du connecteur, semver : elle monte avec tout commit qui change sa description ou son client (« Contrôles »). |
| `api_version` | oui | Version de l'API tierce, telle que l'éditeur la nomme. |
| `base_url` | sauf `base_urls` ou tout `handwritten` | Racine `https://` des chemins d'appel, sans `/` final ; gabarit possible sur les réglages. |
| `base_urls` | non, exclusif de `base_url` | Une racine par valeur d'un réglage `choice` : `{ setting: region, values: { us: …, eu: … } }`. |
| `auth` | oui | Mode d'authentification, voir « Le compte ». |
| `credential` | sauf `none` et `oauth2_user` | Champs fournis par le consommateur : `name`, `label`, `secret` (booléen), `holder` (`account` par défaut, ou `host`), voir « Le compte ». |
| `account_identity` | non | Identité d'un compte rattaché chez un tiers : `name`, `label`, `pattern` (expression ancrée), citée par `base_url` seulement, voir « Le compte ». |
| `settings` | non | Réglages non secrets d'un compte, voir « Le compte ». |
| `modes` | oui | Qui peut porter un compte : `platform`, `byo_user`, `byo_org`. |
| `timeout_s` | non (30) | Délai d'un appel, en secondes, de 1 à 300 (le plafond qu'exécute le paquet d'oto 2) ; une fonction peut déclarer le sien. |
| `quota` | non | Quota par défaut sur une clé de la plateforme ; n'existe que si `modes` contient `platform`. |
| `query_arrays` | non | Encodage des listes en query : `repeat`, `brackets`, `comma`. |
| `headers` | non | En-têtes constants de toute requête : `{ Notion-Version: "2025-09-03" }`. Jamais un secret ni l'en-tête d'authentification. |
| `rate_limit` | non | Rythme maximal du tiers, par credential : `{ requests: 4, seconds: 1 }`. |
| `probe` | non | Sonde de la connexion : `{ function: get_company, non_empty: [scopes] }`, une lecture sans argument requis, jamais décomptée d'un quota ; chaque chemin de `non_empty` doit être non vide dans sa réponse ; `balance`, le solde d'un compte payant (voir « Sonde à solde »). |
| `errors` | oui | Table commune à toutes les fonctions : `status` (un ou plusieurs codes HTTP), `code` (refus nommé), `message` (anglais), `retryable`, et facultatifs `body` (condition sur le corps) et `marks_account` (voir « Signal de refus du service ») ; la première entrée qui s'applique l'emporte. |

### Le compte

Un compte garde tous les champs que déclare `credential` (les secrets chiffrés par l'hôte) et ses réglages, `settings` : `name`, `label`, `type`, et selon le type, `choice` (`choices`, liste fermée, `default` facultatif : `{ name: region, label: Data region, type: choice, choices: [us, eu], default: us }`), `text` (`pattern`, expression ancrée : `{ name: domain, label: Domain, type: text, pattern: "^[a-z0-9-]+$" }`) ou `url` (adresse `https://` libre, saisie par un admin : serveur d'un standard, site).

Un réglage n'est cité que par une adresse. `base_url`, `token_url` et `authorize_url` sont des gabarits : `https://{domain}.example.net` (domaine d'un tenant), `{server}/xapi/v1`. Un réglage `url` (ou une valeur de `from_token`) ne se cite qu'en tête, à la place du schéma et de l'hôte ; un autre réglage, qu'après `https://`. `base_urls` et `token_urls` donnent une adresse à chaque valeur d'un `choice`, quand les hôtes ne se déduisent pas l'un de l'autre. L'exécution garde ces adresses : `https` seul, jamais un hôte qui résout vers une adresse interne, aucune redirection suivie ; une valeur `text` ou `choice` ne porte que lettres, chiffres, `-` et `_`.

`auth.kind`, chaque secret nommant un champ de `credential`, jamais une valeur :
- `api_key` : `in` (`header` ou `query`), `name` (de l'en-tête ou du paramètre), `key`, `prefix` en en-tête seulement : `{ kind: api_key, in: header, name: X-Claap-Key, key: api_key }` ;
- `bearer` (`token`) ; `basic` (`username`, `password`, deux champs) ;
- `oauth2_client_credentials` : `token_url` ou `token_urls`, `token_request` (`json`, `form`), `client_auth` (`body` ou `basic` : où vont l'identifiant et le secret du client), `client_id`, `client_secret`, `scope` et `expires_in_default` facultatifs ;
- `oauth2_user`, le consentement d'une personne (code d'autorisation) : `authorize_url`, `token_url` ou `token_urls` (corps en formulaire), `client_auth`, `scopes`, `authorize_params` (constantes, jamais un paramètre que pose l'hôte : `client_id`, `redirect_uri`, `state`…), `pkce: S256`, `refresh` (`refresh_token` avec `rotates` booléen, `exchange` avec `exchange: { grant_type, token_param }`, ou `none`), `expires_in_default`, `identity: { function: get_me, path: userPrincipalName }` (qui a consenti, pour nommer le compte : une lecture sans argument requis), ou, quand l'API n'a pas de telle lecture, `identity: { url, path, scopes }` : une adresse complète en `https`, fixe (ni gabarit, ni query), hors de `base_url` (le service d'identité commun du fournisseur), lue en `GET` avec le jeton et sans argument, et les droits qu'elle exige, que le consentement demande à chaque niveau, `from_token: [instance_url]` (champs de la réponse de jeton gardés avec le compte, citables par `base_url`) ; à la place de `scopes`, `access_levels` et `scope_implies`, les niveaux d'accès ([niveaux d'accès](niveaux-d-acces.md)) ;
- `none`.

En `oauth2_user`, `credential` est interdit : les jetons du consentement ne sont pas des champs, et `client_id`/`client_secret` appartiennent à l'application OAuth (celle de l'hôte par défaut, celle de l'organisation si elle en pose une), pas au compte ni au fichier.

**Compte de l'hôte et compte rattaché.** Un champ de `credential` porte `holder` : `account` (par défaut : saisi avec le compte) ou `host` (fourni par l'application hôte, une fois pour toutes ses organisations ; jamais stocké avec le compte, montré ni saisissable). Un compte rattaché chez un tiers qui héberge les comptes de ses utilisateurs (une messagerie hébergée : LinkedIn, WhatsApp…) déclare `account_identity` : `{ name: account_id, label: LinkedIn account, pattern: "^[A-Za-z0-9_-]{1,64}$" }`, l'identifiant du compte chez le tiers, une valeur par compte. Il ne se cite que dans `base_url` (`https://api.unipile.com/v2/{account_id}`), ou dans chaque adresse de `base_urls`, après l'hôte (jamais à la place du schéma ou de l'hôte), et dans aucune autre adresse ; aucun argument, paramètre de chemin, de requête, de corps ou d'en-tête, ni aucune constante ne porte son nom, ni aucun champ de `credential`, réglage ou valeur de `from_token`, et la fabrique le refuse : l'agent ne le fournit jamais, il vient du compte que la règle de partage de l'hôte a désigné. Un connecteur dont tous les champs sont `holder: host` est valide : le compte n'a alors que son identité. L'hôte assemble à l'appel son secret, les champs du compte et l'identité ; il écrit l'identité par un seul service qui la vérifie auprès du tiers, jamais par une saisie (la clé de l'hôte atteint tous les comptes de son abonnement).

```yaml
connector:
  name: linkedin_unipile
  base_url: https://api.unipile.com/v2/{account_id}
  auth: { kind: api_key, in: header, name: X-API-KEY, key: api_key }
  credential:
    - { name: api_key, label: Unipile API key, secret: true, holder: host }
  account_identity: { name: account_id, label: LinkedIn account, pattern: "^[A-Za-z0-9_-]{1,64}$" }
```

### Le bloc `functions`

| Champ | Obligatoire | Sens |
|---|---|---|
| `name` | oui | Un verbe et son objet : `list_estimates`. |
| `class` | oui | `read`, `write` ou `sensitive`. |
| `act` | non (déduit de la classe) | La fonction engage ou détruit (envoi, corbeille, archive, déplacement) : booléen, `false` par défaut pour `read`, `true` pour `write` et `sensitive`. Une simple préparation, comme un brouillon, déclare `act: false`. Jamais `false` sur `sensitive`, jamais `true` sur `read` (la fabrique refuse). |
| `scopes` | si le connecteur a des niveaux d'accès, interdit sinon | Les droits OAuth que la fonction exige, tous ([niveaux d'accès](niveaux-d-acces.md)). |
| `description` | oui | En anglais, 1000 caractères au plus (borne du paquet d'oto 2) : ce que l'agent lit. |
| `input` | oui | JSON Schema 2020-12 d'un objet strict (`type: object`, `additionalProperties: false`, `properties`), servi et validé tel quel. |
| `examples` | oui, au moins un | `title` et `input`, chaque `input` validé contre `input`. |
| `refusals` | non | `code`, `when` (statut HTTP ou condition), `message` : surcharge ou complète la table commune ; sous un statut seulement, `body` et `marks_account` comme dans la table. |
| `checks` | non | Contrôles de l'entrée avant l'appel, chacun nomme un refus : `{ kind: equal_sums, refusal: entry_unbalanced, items: ledger_entry_lines, fields: [debit, credit] }` (sommes égales, chaînes décimales sommées exactement). |
| `expect` | non | Contrôles de la réponse, chacun nomme un refus : `{ kind: non_empty, refusal: pdf_missing, path: public_file_url }`. |
| `call` | sauf `handwritten` | `method`, `path` relatif avec `{param}`, puis `query`, `body` (envoyé quelle que soit la méthode, `DELETE` compris), `headers` qui associent un nom côté API à un argument ; `constants` (`query`, `body`, `headers`) : des valeurs envoyées à chaque appel, hors du schéma, comme `{ body: { draft: true } }` ; `encode` : `{ filter: json }` sérialise un argument structuré en une chaîne. Chaque argument va à un seul endroit, chaque nom côté API reçoit une seule valeur. |
| `handwritten` | exclusif de `call` | `python` (`module`, `function`) et `typescript` (`file`, `export`). |
| `pagination` | non | `kind` (`cursor` ou `page`), `request_param`, `next`, `more` facultatif (booléen de la réponse, `false` à la dernière page : `has_more`), `total` facultatif, `max_pages`. Présente, elle ajoute `all_pages` et `max_pages` au schéma servi. |
| `output` | non | `items` (chemin de la liste), `strip` (clés retirées), `projection` (clés gardées). |
| `timeout_s` | non (celui du connecteur) | Délai propre à la fonction, en secondes, de même type et mêmes bornes que celui du connecteur, qu'il remplace pour chacun de ses appels (chaque page d'une lecture paginée) : plus court (une page qui peut rester pendue) ou plus long (une réponse d'IA synchrone de plusieurs minutes), jamais égal (la fabrique refuse, règle 11). |
| `cost` | non | Unité décomptée : `per: request` ou `per: page`. |
| `confirm` | si `sensitive` | `summary`, gabarit du résumé montré avant exécution (`Validate invoice {id}: irreversible.`). |

**Lire et agir.** Chaque connecteur à effet se partage en deux côtés : `<connecteur>` (lire et simuler, brouillon compris) et `<connecteur>_act` (tout ce qui engage ou détruit : envoi, corbeille, archive, déplacement). Le partage se lit sur `act`, fonction par fonction : une seule description, un seul compte, et l'hôte sert les fonctions `act` sous le nom `<connecteur>_act.<fonction>`, les autres sous `<connecteur>.<fonction>`. `class` dit ce que fait une fonction et si elle se confirme ; `act`, de quel côté elle est servie : un brouillon est une écriture (`write`) qui reste du côté lecture (`act: false`).

**Délai par fonction** (décidé le 16/10, écrit le 19/10) : `timeout_s` sur une fonction remplace, pour elle seule, celui du connecteur, plus court ou plus long. La sortie TypeScript le porte en millisecondes (`timeoutMs` de la fonction, à côté de celui du connecteur) :

```yaml
connector:
  timeout_s: 120
functions:
  - name: get_company
    call: { method: GET, path: "/linkedin/company/{identifier}" }
    timeout_s: 60
```

Décidé le 16/10, pas encore écrit :
- **Fichiers** : un type `file` en entrée et en sortie, et le corps multipart. Le pointeur est toujours un fichier de l'hôte, effacé après le transfert ; une destination ne reçoit qu'un identifiant de fichier de l'hôte.

### Signal de refus du service

La description dit comment le service signale qu'il refuse la clé du compte ou que ses crédits sont épuisés, pour que l'hôte marque le compte et lève la marque au premier appel réussi. Une entrée de `errors`, ou un refus d'une fonction dont `when` est un statut, porte :
- `marks_account` : `credential_rejected` (le service refuse la clé ou le jeton du compte : clé invalide ou révoquée, session déconnectée, jeton révoqué) ou `quota_exhausted` (crédits ou quota de l'offre épuisés) ;
- `body`, facultatif : une condition sur le corps JSON de la réponse, `{ path, equals }`, la valeur au chemin pointé (un indice de liste en chiffres : `errors.0.extensions.code`) égale à l'une des valeurs listées (texte, entier ou booléen). L'entrée ne vaut que si la condition tient ; sinon l'hôte essaie l'entrée suivante du même statut.

Seul ce qui est déclaré marque : aucune entrée ne marque par défaut, un 401 compris. Une condition sur le corps dit un refus que le statut ne distingue pas : une erreur GraphQL sous un 200, un code d'erreur sous un 400.

```yaml
errors:
  - { status: 400, body: { path: error.code, equals: [190, 102] }, code: authorization_expired, retryable: false,
      marks_account: credential_rejected, message: "Meta no longer accepts this authorization (Graph error code 190 or 102): reconnect the account." }
  - { status: 400, code: invalid_request, retryable: false, message: "Meta rejected the request: check the ids, fields and parameters." }
  - { status: 401, code: authorization_expired, retryable: false, marks_account: credential_rejected, message: "…" }
  # une erreur GraphQL sous un 200 :
  - { status: 200, body: { path: errors.0.extensions.code, equals: [UNAUTHENTICATED] }, code: key_refused, retryable: false,
      marks_account: credential_rejected, message: "…" }
```

La fabrique refuse (règle 10, [fabrique](fabrique.md)) : `body` ou `marks_account` sur un refus dont `when` est une condition en texte, que l'hôte ne sait pas évaluer ; un statut 2xx sans condition sur le corps, qui ferait de chaque succès un refus ; `credential_rejected` sur un 403 sans condition (un droit manquant n'est pas une clé refusée) et `quota_exhausted` sur un 429 sans condition (un débit dépassé n'est pas un crédit épuisé) ; une entrée qui marque et se dit rejouable ; une entrée à condition placée, dans sa table, après une entrée sans condition qui partage un de ses statuts, et qui ne serait donc jamais lue.

Déclarent `marks_account: credential_rejected` sur leur 401, que leur table dit déjà clé ou jeton refusé : `affinity`, `claap`, `fod`, `klaviyo`, `mailpool`, `modjo`, `nextmotion`, `notion`, `pappers`, `pennylane_firm`, `sivan`, `typeform`, `wttj_ats`, `yousign`, `linkedin_unipile` (session LinkedIn déconnectée, une clé refusée pour ce compte) et `meta_ads`, qui marque aussi les codes Graph 190 et 102 sous un 400 (ils remplacent le refus en texte que ses fonctions portaient). Ne marquent rien, faute de certitude : `aircall`, `amplitude`, `pennylane` et `sellsy`, dont la même entrée couvre 401 et 403 ; le 402 de `sellsy` (« quota de l'offre atteint pour cette ressource », pas un crédit du compte) et le 403 de `pappers` (crédits épuisés ou droit manquant, que le statut ne distingue pas) ; le 401 de `microsoft_app` (`oauth2_client_credentials`, dont l'hôte renouvelle le jeton) ; les codes 4, 17, 32, 613 et 80000 à 80014 de `meta_ads` (des débits). Les connecteurs `oauth2_user` ne déclarent rien : leur 401 relève du renouvellement du consentement par l'hôte.

### Sonde à solde

La sonde d'un compte payant lit aussi son solde quand l'API du service le permet. Une sonde qui ne teste que l'autorisation répond « sain » sur un compte à zéro : la clé vaut, l'appel réussit. Lire un solde n'est pas le vérifier : `balance` dit où le lire et sous quel seuil la sonde n'est pas saine.

```yaml
probe: { function: get_account, balance: { path: credits.remaining, min: 1, unit: credits } }
```

- `path` : chemin pointé du solde dans la réponse de la fonction de sonde, un indice de liste en chiffres (`accounts.0.balance`) ; chaque segment est non vide, sans espace.
- `min` : le seuil, un nombre positif ou nul. Un solde égal ou supérieur est sain ; sous le seuil, absent ou qui n'est pas un nombre JSON (un texte `"12"` compris), la sonde n'est pas saine : un solde illisible ne passe jamais pour sain.
- `unit` : ce que compte le solde, tel que l'éditeur le nomme (`credits`, `requests`, `EUR`), rendu avec la valeur et le seuil.

On ne paie pas pour savoir si l'on peut payer : la fonction d'une sonde à solde ne déclare pas de `cost` (la fabrique refuse, règle 5), et le commentaire du fichier cite la source qui établit que l'appel de solde est gratuit et le chemin où le lire. Un solde qui se calcule (crédits de l'offre moins ceux consommés, plus un crédit prépayé) ne se dit pas : `path` lit une seule valeur. Sans source qui établisse le chemin et la gratuité, le fichier ne déclare pas de solde.

Aucune description ne déclare encore de solde. Écartés au relevé du 2026-10-19, faute de source qui établisse un appel gratuit et un chemin unique : `pappers` (son suivi de crédits rend les crédits de l'offre, ceux consommés et le prépayé restant, sans solde en une valeur, et la référence ne dit pas l'appel gratuit) ; `affinity` (le quota mensuel du compte se lit à une route que la référence v1 dit exemptée de ce quota, mais la description ne la porte pas, la route v2 qu'appelle le client n'est pas dite exemptée, et la valeur rendue pour une offre sans limite n'est pas documentée) ; `sellsy` (le quota restant ne se lit que dans des en-têtes de réponse) ; `claap` (quota d'enregistrement de l'offre, sans lecture) ; `mailpool` (des actions facturées en crédits, sans lecture de solde ni dans son client ni dans le code d'oto 1). Les autres connecteurs décrits n'ont aucune lecture de solde, ni dans leur client, ni dans le code d'oto 1, ni dans leur description, ou signent avec la clé de l'hôte (`linkedin_unipile`).

### Le bloc `exposure`

L'exposition est une projection, pas une propriété de la fonction. `mode` vaut `per_action` (un outil `<namespace>_<name>` par fonction), `per_connector` (un outil par connecteur, l'action en paramètre) ou `via_call` (rien n'est exposé, le verbe d'appel lit le registre). Le défaut est `per_connector`, fixé par le consommateur ; `mode` le surcharge pour un connecteur, `tool` nomme l'outil unique en `per_connector`.

`exposure` et `modes` ne servent qu'à oto 1 : un hôte d'oto 2 sert ses fonctions par des outils fixes et dit qui fournit le compte par son propriétaire. Les deux blocs restent, marqués « oto 1 seulement », et partent quand oto 1 ne lira plus ce dépôt (décidé le 16/10).

### Le premier fichier : Sellsy

`connectors/sellsy/connector.yaml` décrit deux fonctions de lecture, `list_estimates` (pagination par curseur, dix pages au plus) et `get_estimate` (refus `estimate_not_found` sur 404), derrière `oauth2_client_credentials` en corps JSON. Ses valeurs ont été vérifiées le 30/09 contre la référence publique de l'API Sellsy v2 (spec v2.300.0) : champs de tri, `embed` de la liste et du détail, coût par requête, requête de jeton.

```yaml
functions:
  - name: get_estimate
    class: read
    description: Get the full record of one Sellsy estimate by its id.
    input: { type: object, additionalProperties: false, required: [id], properties: { id: { type: integer } } }
    examples: [{ title: One estimate with its company, input: { id: 42, embed: [company] } }]
    refusals:
```

### Contrôles

`tests/test_connector_descriptions.py` vérifie que le schéma est un JSON Schema valide, que chaque description le respecte et porte le nom de son dossier, et que chaque exemple respecte l'entrée de sa fonction. Cinquante-deux variantes invalides du fichier Sellsy doivent être refusées : classe absente, clé inconnue, `call` et `handwritten` ensemble ou aucun des deux, fonction sensible sans `confirm`, entrée non stricte, aucun exemple, exemple hors bornes ou à argument inconnu, `embed` non documenté, `token_url` absent, `credential` absent, `quota` sans `platform`, version hors semver, `exposure.mode` inconnu, schéma de sortie ouvert ou sans propriétés, `rate_limit` incomplet, en-tête constant non textuel, encodage inconnu, contrôle d'un genre inconnu, attente sans chemin, sonde à clé inconnue, `more` vide ; et pour le compte : `client_auth` absent, `token_url` et `token_urls` ensemble, `base_url` et `base_urls` ensemble, liste fermée d'une valeur, `text` sans motif ou à motif non ancré, `url` à liste, gabarit à `/` final, clé en query préfixée, clé sans place, `oauth2_user` avec un credential, avec `client_id`, sans identité, `rotates` hors `refresh_token`, `exchange` sans sa demande, paramètre d'autorisation réservé à l'hôte, PKCE inconnu ; pour l'identité à une adresse, sept de plus : sans droits ou à liste vide, avec aussi une fonction, hors `https`, avec une query, en gabarit, sans chemin ; pour le compte de l'hôte et le compte rattaché, six de plus : `holder` inconnu, champ fourni par l'hôte dans un `oauth2_user` (credential interdit), identité à motif non ancré, sans motif, à nom invalide, à clé inconnue ; et pour les niveaux d'accès, treize de plus : niveaux et `scopes` ensemble, sans `full`, `full` seul, niveau sans droits ou à liste vide, à clé inconnue ou à nom invalide, `scope_implies` sans niveaux ou à liste vide, niveaux hors `oauth2_user`, `scopes` d'une fonction sans niveaux, fonction sans `scopes` ou à liste vide dans un connecteur à niveaux ; et pour le signal de refus du service, six de plus : marque inconnue, condition sans `equals`, à liste vide, à valeur qui n'est ni texte ni entier ni booléen, à clé inconnue, à chemin vide ; et pour la sonde à solde, onze de plus : chemin vide, à point en tête ou en fin, à segment vide, à espace, seuil qui n'est pas un nombre ou négatif, unité vide, clé inconnue, sans seuil, sans unité ; et pour le délai d'une fonction, six de plus : nul, négatif, non entier, en texte, `null`, au-delà de 300 s (borne qui vaut aussi pour le connecteur). Les règles hors schéma sont vérifiées par la fabrique ([fabrique](fabrique.md)). `jsonschema` est un outil de test, pas une dépendance de la lib.

Deux gardes de CI, décidées le 16/10 et écrites le 19/10 :

- **Un client, une description.** Un client de la lib est une entrée directe de `oto/tools/` (paquet ou module), ou un sous-paquet d'une famille (`google`, un paquet par service). Le code qu'une description couvre est le client du même nom que le connecteur, entier, ou ce que `described_by` de `connectors/clients.yaml` y rattache : un client entier d'un autre nom (les paquets Google à `gmail`, `google_drive`, `google_calendar` et `google_sheets`), ou seulement des fichiers d'un client, le reste du client n'étant alors le code d'aucun connecteur (`microsoft` : la surface fichiers, le consentement, ses droits et le transport commun, pas le courrier, l'agenda ni Teams ; `linkedin_unipile` : le transport commun et les familles d'appels décrites, pas la recherche, le fil ni les produits premium). Un client sans description est nommé dans `without_description`, avec une catégorie et sa raison. Trois catégories de principe admettent une entrée nouvelle : `not_a_service_client`, `not_describable` (le format ne sait pas le dire), `oto_service` (client d'un service d'oto) ; deux catégories en attente ne font que décroître : `before_the_rule` (antérieur à la règle du 05/10) et `not_described_yet`. `tests/test_clients_described.py` refuse un client qui n'est ni décrit ni nommé, et une entrée qui ne dit plus vrai (client ou fichier absent, connecteur sans description, exception dont le client a reçu sa description). Au 19/10, 122 exceptions : 6 `not_a_service_client` (utilitaires communs, nœud HTTP générique, Markdown, PDF, navigateur, code NAF), 7 `not_describable` (les six clients du paragraphe précédent, et un client sans API publique), 2 `oto_service`, 3 `not_described_yet` (ajoutés après la règle du 05/10 sans description) et 104 `before_the_rule`.
- **Gardes par commit.** `python -m fabrique.commits <avant> <après>`, lancé par le job `commits` de la CI avec l'historique entier, juge chaque commit nouveau d'une PR (de sa base à sa tête) ou d'un push de `main` (d'avant à après), un par un, contre son premier parent : le verdict ne dépend ni du regroupement des commits ni d'un rejeu. Un avant inconnu (premier push, `0000…`) ne fait juger que le commit de tête, et la sortie le dit ; un commit antérieur à `connectors/clients.yaml` (une PR ouverte avant la garde) est jugé avec celui de la tête ; un commit de fusion n'est jugé que sur ce qu'il change lui-même. Ni un tag ni un dispatch ne la lancent. Deux règles. *La version monte avec le code* : quand un commit change le code d'un connecteur (tout fichier de `connectors/<nom>/`, et son client tel que rattaché ci-dessus) qui existe avant et après lui, `connector.version` monte (semver), ou le commit porte dans son bloc de trailers, celui de `Changelog:`, la dispense `Version-dispense: <connecteur> — <raison>` (tiret cadratin), qui ne vaut que pour lui ; `Version-dispense: * — <raison>` dispense tous les connecteurs du commit, seulement s'il touche `connectors/connector.schema.json` ou `fabrique/` (une passe sur tout le format). Une version qui descend n'est jamais dispensée ; une dispense mal formée, hors du bloc de trailers, ou globale sans passe sur le format fait échouer le commit, dont le message d'échec donne la version cible ou la ligne à ajouter. La lib commune, la fabrique, la sortie générée, les tests et la version de la lib (`pyproject.toml`, `uv.lock`, le paquet npm, qui suivent le flux de publication) ne sont le code d'aucun connecteur : un commit de publication ne regarde aucun connecteur. Un correctif urgent passe par une dispense motivée. *Les exceptions en attente ne font que décroître* : un commit n'ajoute aucune entrée aux catégories `before_the_rule` et `not_described_yet` ; un client nouveau entre au format, ou dans une catégorie de principe avec son motif. Tests : `tests/test_commit_guards.py`. Une PR fusionnée par squash garde ses dispenses seulement si le message du commit fusionné les reprend en trailers.

## Décisions et alternatives écartées

- **Du code source dans l'un des deux langages** : écarté le 29/09. L'autre langage n'en serait qu'une traduction ; un fichier déclaratif se lit des deux côtés.
- **TOML** : écarté, illisible dès trois niveaux d'imbrication, qu'un schéma d'entrée dépasse souvent. **JSON seul** : écarté, sans commentaires et pénible pour une description sur plusieurs lignes.
- **Référencer la spec OpenAPI de l'éditeur** (`operation: getEstimates`) et n'ajouter que classe, refus, exemples et projection : non retenu à ce jour. Moins à écrire, mais chaque connecteur dépendrait de la qualité d'une spec tierce.
- **Un client ajouté à la lib sans description** : écarté le 2026-10-05. Tout client entre au format ; une fonction ou un client que le format ne sait pas dire est nommé, avec sa raison, dans « Les connecteurs décrits ».
- **L'outil MCP comme unité** (le modèle d'oto 1, où le nom de l'outil est le contrat et où Sellsy est servi par `sellsy_document(kind, op)`, quatre documents de vente fusionnés) : écarté. L'unité est la fonction ; l'outil, une projection. Cela répond au point « verbe `oto_call` ou outils dédiés » d'ADR 0070 §7.8 : les deux, par projection.
- **Un langage d'expressions pour les contrôles** (une formule « débits = crédits ») : écarté le 06/10. Des genres fermés et nommés (`equal_sums`, `non_empty`), chacun lié à un refus de la table, se lisent et s'exécutent pareil dans les deux langages ; un genre s'ajoute quand une description en a besoin.
- **Refus en texte libre** : écarté. Une table structurée (`code`, `when`, `message`) que la fabrique traduit en erreurs typées dans les deux langages.
- **Une seule version** : écarté. La version du fichier (semver) et celle de l'API tierce (en clair) sont deux champs.
- **Convertir les 713 outils existants, ou leur attribuer une classe** : écarté. La classe s'écrit à l'entrée d'un connecteur dans le format.
- **Garder les descriptions en français** : écarté. Ce que lit l'agent est en anglais ; une description française se traduit à son entrée.
- **Un seul secret par compte, l'adresse ou la région dans un champ du credential** : écarté le 2026-10-08. Un compte garde tous ses champs ; une région ou une adresse est un réglage non secret, typé (liste fermée, motif, adresse libre gardée à l'exécution), cité par un gabarit, que l'écran de l'hôte propose et que l'exécution vérifie.
- **Un connecteur par région** (`typeform_eu`) : écarté le 2026-10-08 ; les fonctions et le contrat ne changent pas avec l'hôte.
- **`oauth2_user` renvoyé à du code écrit à la main, le jeton passé en `bearer`** : écarté le 2026-10-08. Le consentement (adresses, scopes, PKCE, renouvellement, rotation, identité) se décrit, et l'hôte l'exécute une fois pour tous.
- **L'identifiant et le secret du client OAuth dans `credential`** : écarté le 2026-10-08. Ils appartiennent à l'application (de l'hôte, ou de l'organisation qui pose la sienne), pas au compte d'une personne.

## Sécurité et confidentialité

- Le fichier ne porte aucun secret : il nomme les champs du credential (`secret: true`) et `auth` y renvoie par leur nom ; un réglage n'est jamais un secret. Une clé passée en query (`in: query`) est admise : le tiers l'a voulue là et la voit de toute façon ; l'exécution la masque dans tout journal, adresse comprise. Le secret est fourni par le consommateur à chaque appel ; la lib n'en lit aucun (garde `tests/test_no_secret_read_guard.py`).
- Une adresse saisie par un admin (`url`, valeur de `from_token`) n'est suivie qu'en `https`, vers un hôte qui ne résout jamais vers une adresse interne, sans redirection ; le format le déclare, l'exécution le garde.
- `base_url` nomme la racine documentée de l'API de l'éditeur. Une coordonnée tirée du front d'un tiers (clé d'API publique, identifiant d'application) n'entre jamais dans un fichier (`docs/conventions.md`).
- Le dépôt est public : un connecteur dont l'accès appartient à un client, son propre back-office, n'a pas de description ici ; c'est un connecteur propre à son hôte.
- Un message de refus dit le fait, au plus une condition, jamais le nom d'un outil : la lib ne connaît pas les outils de l'appelant.

- Référencer la spec OpenAPI de l'éditeur quand elle existe ?
